# Development and tests

```bash
pnpm test           # unit tests: core (parsing, write-back, the jQuery session, statement splitting, undo relocation, slides, design systems, dashboards, docs), the importer, the exporter (what a browser can write, font inlining), and the UI strings (same keys and placeholders in both languages, every key the code uses exists, no hard-coded Chinese in code), and that every ✓ in the cross-kind matrix (`.design/project-kinds.md` §3) names its e2e suites or why none checks it yet in `e2e/coverage.json`
pnpm typecheck
pnpm knip           # dead code: unused files, exports and dependencies
pnpm depcheck       # which package may import which
pnpm tingly-design --help   # the command line from source (docs: cli.md)
```

## PPTX module smoke corpus

The standalone converters have a checked-in corpus in [`packages/core/test/fixtures/pptx-smoke/`](../../packages/core/test/fixtures/pptx-smoke/README.md). Its README describes the pages, expected success/refusal, deterministic regeneration and validation limits. Run the module smoke without starting the editor:

```bash
pnpm --filter @dc/core exec vitest run test/pptxSmoke.test.ts
```

Optional independent schema validation uses .NET and Open XML SDK; see [`scripts/validate-pptx/README.md`](../../scripts/validate-pptx/README.md). It is developer tooling, not a runtime or CI prerequisite.

This is not a product e2e suite: PPTX menus and CLI integration are not enabled. Package/XML checks and conversion assertions do not replace independent Office rendering. The corpus includes separate supported and unsupported cases because one unsupported object currently rejects the whole import atomically.

## End-to-end suites

The other suites select elements by their Chinese labels, so they run the browser with a `zh-CN` locale; `i18n.py` covers English.

`pnpm e2e` runs every suite below but `delegate` with one command: it starts what each group needs (`pnpm dev` with the mock model, `pnpm dev` with no model for `ai_settings`, `pnpm build` for the suites that start their own server, `pnpm bundle` for `embed`), runs the suites one after another and prints one table (`--jobs 4` runs four slices side by side, each in its own copy of the checkout with its own ports; `--shard 2/4` runs one slice, which is how CI spreads the set over four runners); `e2e/out/report.md` and `report.json` say which checks failed, with each suite's output in `e2e/out/logs/`. `pnpm e2e slides docs` runs only those, `--smoke` the per-PR subset, `--list` shows the groups, `--real` adds `delegate`. The suites edit the sample projects and put them back with `git checkout`, so it refuses to start while `projects/` has uncommitted changes (`--force` runs anyway). The whole set takes about fourteen minutes in one line, a quarter of that in four.

`pnpm eval` is a different kind of check: it has headless Claude Code do the same design task once with the skills and the command line and once with the MCP server, then scores what it left behind and prints one comparison (pass or fail, tool calls, `check` and `look` rounds, cost, time). It needs `claude` signed in and Chrome, costs a few dollars and takes minutes, so it is not part of `pnpm test`, `pnpm e2e` or CI. `pnpm eval -- --list` shows the tasks, `--task`, `--route`, `--runs`, `--model`, `--judge` (a second look at the final picture) and `--cli "node dist/tingly-design/cli.mjs"` (evaluate a bundle or the npm package instead of the source) choose what runs. Results land in `evals/out/`. Its pure parts (reading a transcript, scoring) are unit-tested by `pnpm test`; the design is in `.design/agent-evals.md`.

Each suite can still be run on its own. The end-to-end tests need `pnpm dev` running and Python Playwright (`pip install -r e2e/requirements.txt`). Set `DC_CHROME=/path/to/chrome` to use another browser (`pnpm e2e` picks Playwright's headless shell when it is installed); in a headless environment use Playwright's `chromium_headless_shell`, because full Chromium in headless mode misplaces clicks inside a zoomed artboard.

## E2E in CI

`.github/workflows/e2e.yml` runs `pnpm e2e` on three schedules, because the full set is too slow for every pull request: every night on main and by hand from the Actions tab, through `e2e-patrol.yml` (the full set; a red night opens one issue labelled `e2e-patrol`, or comments on the open one, and a green night closes it; a run by hand only reports), before every release (the full set, blocking), and on a pull request that touches `apps/`, `packages/`, `e2e/` or `projects/` (`--smoke`). The full set runs as four slices, one job each, so a run takes the time of its slowest slice; the report and the logs are the run's `e2e-report-<slice>` artifacts. The full set includes `baseline`, the editor's screenshots compared with the `e2e-baselines` branch; when a change to the editor's look is meant, look at the diffs in the red run's report, then run the E2E patrol workflow by hand with "record baselines" ticked, which takes the screenshots again on the same runner and pushes them to that branch. Why it is split this way: `.design/harness.md`.

## Releasing

Pushing a tag `vX.Y.Z` releases that version; the workflow writes the tag's version into the root `package.json` before it builds, so nothing is bumped on main first. `.github/workflows/release.yml` first runs every end-to-end suite (`e2e.yml`; a red one stops the release), then the unit tests and typecheck, builds the bundle, starts it the way a host does (`.github/scripts/smoke-bundle.sh`), and packs it into `tingly-design-<ver>.tgz`. That one file, with its `.sha256`, is attached to a GitHub release on the tag and published to npm as `@tingly-dev/tingly-design` and as `tingly-design` (the same contents under both names). A tag with a suffix, such as `v0.2.0-rc.1`, makes a prerelease on the `rc` dist-tag; any other goes to `latest`.

npm publishing uses Trusted Publishing only: no token is stored anywhere, and both packages refuse tokens, so outside CI only a maintainer entering a one-time password can publish. Before the very first release a maintainer runs `scripts/npm-bootstrap.sh` once on their own machine (placeholder versions, the trusted publisher, 2FA required), and creates the `production` environment on GitHub.

`.github/workflows/ci.yml` runs the same checks on every pull request, plus `npm pack --dry-run` to list what the package would contain. Why it is built this way, and how npm publishing is authorised: `.design/release.md`.

`.github/workflows/pages.yml` builds the homepage (`site/`) and, on main, deploys it to GitHub Pages. The tingly-design-motion promo on it is rendered by that job from `projects/tingly-design-motion` (`scripts/build-site.sh`), never committed. A maintainer turns Pages on once: Settings → Pages → Source: GitHub Actions.

## Server log

The server writes one line per event to stderr, so you can see what the fast AI and Claude Code are doing without opening the editor:

```
2026-10-14T09:12:03.120Z INFO  fast.start project=demo kind=design model=claude-haiku-5-5 messages=3
2026-10-14T09:12:04.870Z INFO  fast.done project=demo kind=design model=claude-haiku-5-5 messages=3 ms=1750 chars=212 inputTokens=4120 outputTokens=96
2026-10-14T09:12:30.004Z INFO  delegate.start run=3f9a project=demo kind=slides model=default promptChars=48 attachments=0
2026-10-14T09:12:58.331Z INFO  delegate.finish run=3f9a project=demo kind=slides outcome=done ms=28327 steps=6
```

| Event | Level | Fields |
|---|---|---|
| `fast.start` / `fast.done` / `fast.aborted` / `fast.error` | info (error for `fast.error`) | project, kind, model, messages, ms, chars, token counts, error |
| `fast.unavailable`, `delegate.unavailable` | warn | project, reason (no API key, no `claude` CLI) |
| `delegate.start` / `delegate.finish` | info (warn when `outcome=error`) | run, project, kind, model, promptChars, attachments, outcome (`done`, `stopped`, `error`), ms, steps, error |
| `delegate.step` | debug | run, tool, n |
| `request.failed`, `watcher.failed` | error | method, path, file, error |

Prompts and replies are never logged, only their length. Settings (environment variables):

- `DC_LOG_LEVEL`: `error`, `warn`, `info` (default), `debug` or `silent`.
- `DC_LOG_FORMAT=json`: one JSON object per line (`at`, `level`, `event`, fields), for a host that collects logs.
