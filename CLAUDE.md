# Tingly Design

A design editor with two-way editing: canvases, slides, design systems, dashboards, docs and motion pieces are plain files under `projects/<name>/`, edited by hand in the editor, by a fast model, by Claude Code, or in a terminal, all through one write-back engine. It runs alone or embedded in Tingly Box.

Start with `docs/en/architecture.md` for how it works and the repository layout.

# Guideline

Tingly Design ships inside Tingly Box and follows the same working conventions as the Tingly Box repository (its `CLAUDE.md` and `.design/`). When this file is silent, do what Tingly Box does.

## UX-First (highest priority)

The product is the core; **UX always comes first**. When UX conflicts with implementation convenience, push UX further rather than diluting it.

**Before building a new feature or changing an existing one, read this repository's [`.design/ux-principles.md`](.design/ux-principles.md).** Its 12 criteria (organize around the user's question; eliminate mode pickers; one word, one meaning; separate orthogonal axes; concrete values over aliases; smart defaults over toggles; diagnostics on the real path; education inside the product; less visual noise; done ≠ locked; hand over the artifact for the next action; scope side effects to the current surface) end in a checklist. Check new features and PRs against it; a deviation needs a stated reason.

## Frontend

- Icons are Tabler (`@tabler/icons-react`); prefer the shared set in `apps/editor/src/components/icons.tsx` and add new ones there when they are reused.
- No UI text in code. Every string a person sees (labels, `aria-label`, `title`, placeholders, toasts, empty states, server errors, starter copy written into new projects) is a key in `packages/i18n/src/locales/en/<area>.ts` with its twin in `zh/<area>.ts`. Components use `useTranslation()`; other editor code imports `t` from `apps/editor/src/i18n.ts`; the server uses `trOf(c)` / `HttpError(status, key, params)`. English is the default and fallback, Chinese is the other shipped language. Write the English and the Chinese together; keep core free of wording (return data such as `AgentStep.op`, let the editor say it). Model-facing prompts and `.claude/skills/` stay English. `pnpm test` fails on a missing key, a mismatched placeholder, or a Chinese string outside the bundles. See `.design/i18n.md`.
- The editor's look is theme tokens (`apps/editor/src/theme.ts`, synced from Tingly Box's `@tingly/ui` palettes by `scripts/sync-tingly-box-theme.mjs`); use tokens, not raw colours, in editor chrome. Work inside canvases, slides and dashboards keeps its own colours.
- Styles are plain CSS, one file per area under `apps/editor/src/styles/`, pulled in by `styles.css` in cascade order (a later file wins at equal specificity). Put a rule in its area's file; add a file at the position where its rules must win, and keep `agent-dock.css` last.
- Every side column (the right panel, the slide strip, a doc's tabs and comments, a design system's navigation, a dashboard's data sources, the conversation column) is resized by dragging its edge and remembers its width: put a `SideResizer` in a new column and a width variable in its CSS, with the old width as the fallback (`apps/editor/src/sideWidth.ts`, `.design/side-columns.md`). A horizontal band whose content varies (motion's element rows, folded by default) has a fixed, draggable height that does not follow its content: a `BandResizer` and an entry in `BANDS` (`apps/editor/src/bandHeight.ts`, side-columns.md §6).
- Buttons come in three families: `btn` (text, with `primary` / `outline` / `ghost` / `danger` / `sm`), `tb` (the top bar) and `ib` (an icon button, `ib sm` at 24px). A new icon button is `ib` plus an area class that only states what differs; don't restyle a bare button from scratch.

## AI model settings

Which model answers is set in one dialog (`apps/editor/src/components/AiSettings.tsx`, opened from the launcher, `ProjectMenu` and the prompt bar's hint): one connection (Tingly Box suggested, Anthropic, or another address) shared by fast AI and Claude Code, a model name for each (with Tingly Box Claude Code goes through Box's `claude_code` routing, with an optional Box profile typed by name), and Claude Code's own sign-in as the alternative. The values resolve environment > saved > default in `packages/core/src/aiConfig.ts`; the server (`apps/server/src/aiconfig.ts`) owns the file and the key. ImageGen (image generation) is its third job (an OpenAI-style `/images/generations` and `/images/edits` address that follows the connection; a tool given only to Claude Code runs, and only while it is configured: `scripts/image-gen.mjs` over the server's `POST /api/projects/:p/images`, results kept in `uploads/`; `DC_IMAGE_*` override; on by default, with a switch in the dialog that keeps the settings and one per project in the request bar's options row, stored in the project's local `.image.json`). A new model-using feature joins this dialog, not a new place. See `.design/ai-settings.md` and `.design/image-generation.md`.

## Frontend changes come back with screenshots

A PR that changes anything a person sees (the editor, the launcher, the homepage in `site/`) carries screenshots of the result, in light and dark and in both languages where they differ. They go to the `pr-assets` branch and are embedded in the PR description as images (a table: language by light and dark) from `https://raw.githubusercontent.com/tingly-dev/tingly-design/pr-assets/<path>` (the repository is public, so the link renders in place), and the thread that did the work attaches them to its reply. Run `scripts/compress-pngs.sh <dir>` (pngquant, then oxipng) on the pictures before pushing them, and keep each picture's path and `.png` extension: descriptions link by branch and path, and the branch was flattened to one compressed commit once, so don't grow it with uncompressed files.

## Design the editor in itself

`projects/tingly-design-ui-canvas` is a canvas that draws Tingly Design's own UI: how the pieces fit, the shell every kind shares, the launcher, the top bar and menus, one board per kind (a numbered wireframe with notes and its open questions), the agent bar's states and the theme tokens. Before changing anything a person sees in the editor, find its board and draw the change there first; when a PR changes the UI, it redraws the board in the same PR. Boards use the editor's light token values, real UI wording, and placeholders for content. See `.design/self-design.md`.

## Files people bring in

What a person brings into a project (chat attachments, an imported page or picture, an imported Markdown file) is kept under `uploads/` and referenced from there, never copied. The exceptions are a dashboard's data (`data/`, the only place it reads files) and a design system's own fonts and assets. See `.design/import-into-project.md`.

A project can also live anywhere on disk: the launcher's Open a folder, or a full path in the new-project dialog, lists it in `projects/.links.json` under a flat name, and everything else reaches it through `projectDir(name)`, so never build a project path by joining `PROJECTS_DIR` yourself. The bundle (an npm install) keeps its data in `~/.tingly-design/` unless the host sets `DC_PROJECTS`. See `.design/project-folders.md`. Committing (every kind, from the change log) commits only the project's folder to the nearest repository holding it, says which repository and branch first, and when there is none creates one in the project folder on the first confirmed commit (`apps/server/src/git.ts`, `.design/project-git.md`).

A whole project leaves and comes back as one `.zip` (`.design/project-archive.md`): the last two items of every kind's `FileMenu` (with or without the change log and installed design systems), the launcher card's ⋯ and its New menu’s Import a project package (.zip)…, and `tingly-design export <p> --as zip` / `import <file.zip>`. The archive holds project folders side by side plus `tingly-design.json`; what goes in and how a zip is read live in core's `projectArchive.ts`, the folders in `apps/server/src/archive.ts`. Local state (`.git`, `renders/`, `.runs.json`, `.claude-session.json`, `.transcript.jsonl`, `.image.json`) never goes in.

Work also moves to and from Claude's own Design artifacts in their original file layout (`.design/claude-design-format.md`): canvas, slides, design system and dashboard have a "Claude Design package (.zip)" item in the `FileMenu` just before the two project items (`tingly-design export <p> --as claude-design`); the launcher’s Import a project package (.zip)… and `tingly-design import` recognise such a package (a `.zip`, or the folder Claude Code saved from an original artifact, with `project/…` or a dashboard's store documents) from its files, with no mode picker, and a Claude Docs `.md` export too. The launcher’s Import Markdown (.md)… opens a new doc; motion has no original type. Launcher imports are four direct actions (PowerPoint, Markdown, table (`.csv`/`.tsv` becomes a new dashboard, file kept in `data/`), project package), each also accepted on drop, scoped by `chooseProjectArchive(format)` in editor `projectArchive.ts`; they share `importProjectFile` and unchanged server/drop detection. See `.design/launcher.md`. The rules are core's `claudeDesign.ts`, the folders `archive.ts`; user guide `docs/*/guide/claude-design.md`.

A size change takes the content with it: core's `sizeAdapt.ts` (`adaptSize`) rewrites a file's px lengths from the old size to the new (x by width, y by height, type and radii by the smaller factor; holes, `calc()` and `%` untouched), the shared `SizeRows` (W/H, presets, "Your sizes" (a custom size joins on use, its × removes it), switch "Scale the page with the size", the offer of a Claude Code re-layout when the aspect ratio moves more than `ADAPT_RATIO_LIMIT`) is in the canvas panel (`resizeBoard`) and the slides deck panel (`resizeDeck`, every slide); motion's Add size seeds the new format's `data-<format>` overrides from the primary layout (`seedFormat`) and offers the same re-layout (`.design/size-adapt.md`). `boardSizes.ts` has a Devices group (DevTools' phone, tablet and laptop viewports) and one group per region of platform sizes (WeChat, Chinese, global) next to the generic Posts and video sizes; a platform size needs a published figure and an unused pixel size, and its research is in `.research/size-presets.md`.

What a dashboard drew wrong (a `NaN`, a chart or table with nothing in it, labels over each other or cut off) is looked at in the real page: core's `drawnCheck.ts` is one self-contained source run by the open dashboard (its `.runs.json` `drawn` and Sources → problems) and by `check --snapshots`'s layout probe in every frame, so an agent with or without the editor open reads it (`.design/drawn-check.md`).

What the AI knows about a project's settings and what a hand change offers it (`.design/config-awareness.md`): core's `settingsProject` (a `Record<ProjectKind, …>` table of sizes, installed design systems, motion formats, fps and speed, doc look, dataset sources, design-system themes) is reported by `open` and `list --json` and built server-side into every delegated request as `Project settings now`; a setting changed by hand goes through the editor's `recordChange`, which tells Claude Code with the next request what changed and, when `followUpFor` (core's `followUp.ts`, one table per change type) says it is worth one, shows the shared `FollowUp` row in the request bar: send, edit the prepared request, or dismiss, never a run on its own. A new setting a person can change gets a `SETTINGS` entry in every kind it applies to and a `ConfigChange` case (a removal such as `formatRemoved`, or a motion `speed` change, is told to Claude but offers nothing). A motion size is deleted with one toast Undo that restores the overrides and `motion.json` together; the custom sizes a person typed ("Your sizes", `motionSizes.ts`) are shared by the canvas, slides and motion pickers and every kind's size panel, each removable with its ×.

A design system's README ends with a generated "Consuming this system" section (core's `dsGuide.ts`, rewritten with `tokens.css` whenever `tokens.json` changes, between `consuming-this-system` markers; the brand book goes above it): how to link the stylesheet, themes, each colour's variable and fallback, ramps, families, the type styles, and why a canvas artboard or a slide uses the values instead. Font entries may be `.ttc` files, kept as files (`.design/design-system-guide.md`).

A canvas's template values (every artboard's `data-props`, grouped by artboard) are listed in the right panel when nothing is selected, `TemplateValues` over core's `canvasTemplateValues`, with the Tweaks fields and write-back; canvas only on purpose (`.design/canvas-template-values.md`).

Text and colours an artboard's template manages are edited where they are drawn: double-click retypes copy with holes (`Hello {{name}}!`, `{{plan.name}}` in an `<sc-for>` over a list declared in `data-props`) into the literal text or the tweak, holes kept (core's `textRetype.ts`, `retypeText` in the store); text fed only by the script says why it cannot be; the Properties panel shows a colour set by a hole as its real colour and edits the tweak (`.design/template-text-editing.md`; canvas only on purpose).

The canvas's fast AI is told to lay out with flex or grid and gap, not pixel offsets, and one reply may copy a part to another artboard: the other (visible, unlocked) artboards stay out of the sandbox document and a line reaches one only through `board(file)`, with handles of their own (`#b1_dc3`); a part goes over as a `clone()`, a move or a bare handle is refused, and a reply that saved several files is one undo step (`group`). Canvas only on purpose; a whole artboard is still Claude Code's (`FAST_EDIT_CANVAS` in core's `prompt.ts`, `FastEditSession` in `exec.ts`, `.design/canvas-fast-edit.md`).

Importing from a project copies a canvas artboard into a deck or motion piece (`uploads/<canvas>-<board>/`, recorded in the index's `imports`) and shows it as `<x-embed src data-props>`; an artboard declaring `$time` is an effect and draws only from its `time` prop, so motion renders it frame by frame. See `.design/import-from-project.md`.

# Keep these in sync (read this before every change)

Three things drift silently when a session forgets them. Each PR that touches one of them updates it in the same PR, not in a follow-up.

## 1. This file

Update `CLAUDE.md` when a PR adds a project kind, a package or app, a cross-kind feature, a convention, a test suite, or a doc that future sessions must read first. If you had to discover something by reading code that a new session would need on day one, it belongs here or in a doc linked from here.

## 2. `.design/`

`.design/` holds the design notes: why a subsystem looks the way it is, the options weighed, what was decided and what is still open. `.design/README.md` is the index, with a row per note grouped by topic.

- **Before** building a feature or changing a subsystem, read the index and the notes it points to.
- **With** each PR whose core is a new feature, a new project kind, a new file format, a protocol or a non-obvious trade-off, write a note or update the existing one, and its row in the index. A bug fix, a rename or copy change usually needs none; say so in the PR if you skip it.
- Follow the maintenance rules at the top of `.design/README.md` (the same as Tingly Box's): current contract, implementation status, history and proposals kept apart; diagrams in a separate `<topic>.pencil.md`; renames update every reference.
- A note describes the design and the reasoning: the problem, the options weighed, what was decided and why, what is still open. It is not a changelog: no PR numbers, commit hashes or "in this PR we…"; that belongs in git history and the PR description. When the design changes, rewrite the note to the current design instead of appending an entry.
- A note says its status on the first line after the title (`方案` / `研究` / `已实施` …). Keep implemented facts, proposals and history apart.
- `docs/` is the other half: user guides (`docs/*/guide/`) and how-it-works pages (`architecture`, `theming`, `embedding`, `development`). Those are written in both `docs/en/` and `docs/zh/`; change both. `.design/` notes are written once, in either language.

## 3. Features that span project kinds

Most editor features are not "canvas features": the prompt bar, attachments, themes, the UI language, the journal and undo, host messages, export, the launcher card, Claude Code delegation (a project keeps one Claude Code conversation on the server, `.claude-session.json`, which every request continues unless it asks for a new one, `.design/agent-panel.md`) all have to work in every kind. Every kind, motion included, has to plug into every one of them, and so does any kind added later.

**Read `.design/project-kinds.md` before adding a kind or a feature that any kind can reach.** Most per-kind differences are `Record<ProjectKind, …>` tables (`OUTLINE`, `CHECK`, `CARD`, `STARTER`, `DELEGATE`, `FAST_PROMPT`, `KIND_CLI` (the command line's sizes, export formats, pick and fast AI), `KIND_APP`, `PREVIEW`, `KIND_NEW` (the New dialog's questions); `.design/kind-registry.md`), so a new kind fails to compile until each has an entry; don't add another `kind ===` chain where a table fits. It lists every place a kind is registered (core, server, editor, launcher, skills, samples, docs, e2e) and a matrix of which cross-kind features each kind supports, with the known gaps. When you change either, update the matrix in the same PR, and give every ✓ its suites (or the reason none checks it yet) in `e2e/coverage.json`; `pnpm test` fails when the two disagree. When a feature deliberately skips a kind, write that down in the matrix with the reason, so the next session knows it is a choice and not an omission.

Rules of thumb:

- Build a cross-kind feature once, in a shared component or module (`RequestBar` (the one request bar, a card of three rows: head, box, toolbar, `.design/composer.md`; `PromptBar` adds the pointed-at target and Fast AI for canvas, slides and motion, `AskClaude` sends to Claude Code only), `RunFeed`, `AgentBar` (the prompt at the bottom by default, or in an always-open conversation column on the left that every kind shares: `ChatShell` wraps the app, the kinds with a list of their own on the left hand it to `ListColumn` as the column's first tab, the column keeps a transcript of every turn that the server stores in `.transcript.jsonl`; `.design/agent-panel.md`, `.design/chat-panel.md`), `LayerTree`, `attachments.ts`, `NoteBox`, `ImportHere`, `Dialog` (every modal: backdrop, Esc, focus in and back, Tab kept inside, `.design/dialog.md`), `TopBar` (the one top bar of every kind: `ProjectMenu`, the name, `SyncStatus`, the kind's own actions, then one "more" menu with report an issue, star, language and look; floating bars keep only tools, `.design/top-bar.md`), `FileMenu` (the one Import / Export menu each kind hands its export list to, placed in the `TopBar`), `SyncStatus`, `PreviewAs` (the top bar's "Preview as" menu for a work's own look: a dashboard's light / dark page, a design system's theme; the editor's own look stays under "more"), `shortcutHelp.ts` (`KIND_SHORTCUTS`, the keys of each kind as data behind the "Keyboard shortcuts" dialog (the "more" menu or `?`) and the inspectors' key lines; a key added to a handler gets its row there and its words in `common.shortcut.<id>`), `SHOW_VIEW` in `views.ts` (the `Record<ProjectKind, …>` table of how a board, slide, tab or design-system page is shown by id or name: the command line's `--board` / `--slide` / `--tab` / `--view`, `check --snapshots` and the export menu go through it, so a kind never hands its own `pick` to `FileMenu`), `PaneToggles` (a kind's side panes: `KIND_PANE_IDS` in `panes.ts` lists them, the store holds the one open `pane`, `togglePane` / `openPane` change it, and `TopBar` draws the buttons; never a per-kind `side` / `rail` flag or button), `ProjectMenu`, `InlineRename` (renaming in place), `Segmented` (joined choice buttons), `RowMenu` (a list row's ⋯ menu), `ItemMenuItems` (what a slide, scene or tab's menu offers, in one order), `offerUndo` in `undoRemove.ts` (removing a slide, scene, tab, artboard or thread is not asked about: the toast carries Undo; only what cannot be restored, a design system's binary assets, asks, through `askConfirm`; never `confirm()`), `LOCATE` in `locate.ts` (the `Record<ProjectKind, …>` table of how a file a run changed is shown in each kind; no per-kind `onOpen`), `imageExportItems` (the save / copy PNG pair), `host.ts`, `theme.ts`, `local.ts` (what the browser remembers, and files handed to the person), `hooks.ts` (an element's size)), and wire it into every kind's app. Don't copy it per kind.
- Anything a feature tells Claude Code about a kind (paths, what a file may reference) also goes into that kind's skill under `.claude/skills/<kind>/SKILL.md` and its system prompt in `apps/server/src/delegate.ts`.
- Test it in each kind it claims to support, or say in the PR which kinds were not tested.

A canvas or deck is switched to a theme of an installed design system from the right panel's Theme tab (`panel/ThemeTab.tsx`, `panel/themeApply.ts`; canvas and slides only on purpose): one click rewrites the colours (a deck also the type families) that stand for the page, cards, text, lines and accent with the target theme's plain values (core's `theme.ts`: `planTheme` / `planOriginal` / `applyThemePlan`; never `var()`), keeps what the first switch replaced in the index's `theme.base` so the Original look can come back, applies to every slide or the open one in a deck, and is one step of undo (the edit engine's `group`: ⌘Z takes every file back at once) or the toast's Undo. It reaches Claude Code through `recordChange` (`theme` in core's `followUp.ts`) and `settingsProject`; a new place that writes colours into files should not break the "values, not variables" rule (`.design/project-theme.md`).

# Layout

Slides PPTX exchange is implemented in both directions: the launcher's Import PowerPoint (.pptx)… (picker or drop, `POST /api/archive`, CLI `import`) builds a new slides project through core's `importPptx` (strict at the package, best effort per object, source and report kept in `uploads/`), and Slides' FileMenu, CLI and MCP export the whole visible deck (`pptxExport.ts` with the sandbox's `pptxCapture.ts`: native objects first, a picture of the element only where PowerPoint has no object). Ranges (`--slide 2-4`, visible positions) export too, and a PPTX dropped on an open deck appends its slides as one undoable batch. The modules stay independent: core `importPptx`, `@dc/export/pptx` and `@dc/export/pptx-dom`. **Read `.design/slides-pptx.md` before changing these paths**: current contracts, what is verified (the smoke corpus, the browser harnesses, `scripts/pptx-fidelity/`) and what is still unverified (real PowerPoint rendering; `pnpm e2e pptx` is registered, not a passed-run claim) are kept apart there.

# Build and test

```bash
pnpm dev            # server + editor
pnpm test           # core, import and i18n unit tests, and the matrix's e2e coverage (e2e/coverage.json)
pnpm eval           # agent evaluation: the same design task by skill + command line and by MCP, with a comparison table (costs money; not in CI)
pnpm e2e            # every e2e suite with what each needs started, one table and e2e/out/report.md (--smoke, --list, names, --shard I/N, --jobs N)
pnpm typecheck
pnpm knip           # dead code: unused files, exports and dependencies (knip.json; CI fails on new ones)
pnpm depcheck       # which package may import which (.dependency-cruiser.cjs; the same table as docs/en/architecture.md)
pnpm build
pnpm bundle         # dist/tingly-design/, the folder a host ships (and the npm package)
pnpm tingly-design  # the command line from source; the bundle's cli.mjs is the npm `bin`, server.mjs is `serve`
```

CI (`.github/workflows/ci.yml`) runs the unit tests, typecheck and the bundle on every PR. The full e2e set is too slow for that: `.github/workflows/e2e.yml` (read-only, so callers grant it nothing) runs it every night on main through `e2e-patrol.yml` (a red night opens an `e2e-patrol` issue) and before every release (`release.yml` calls it, red stops the release), and only `pnpm e2e --smoke` on a PR that touches `apps/`, `packages/`, `e2e/` or `projects/` (`.design/harness.md`). Releases are tag-driven: a `vX.Y.Z` tag is the version (stamped into `package.json` in CI, so main is never bumped by hand; a `-suffix` goes to npm's `rc` dist-tag, anything else to `latest`); it builds the bundle once and ships that tarball to a GitHub release and to npm as both `@tingly-dev/tingly-design` and `tingly-design` (`release.yml`, `.design/release.md`). The project is Apache-2.0 (`LICENSE`, `NOTICE`); the release fails if `package.json` has no `license`. npm publishing is Trusted Publishing only (environment `production`, no token anywhere; the packages refuse tokens, so only a maintainer with a one-time password can publish outside CI; first-time setup is `scripts/npm-bootstrap.sh`). Never publish or push a release tag without a maintainer asking. Anything added to the bundle ships to npm: `scripts/bundle.mjs` copies only what it names, keep it that way. Shell shared by workflows lives in `.github/scripts/`; lint with `actionlint` and `shellcheck` as Tingly Box's `.github/workflows/AGENTS.md` says.

The command line names each command after the editor's word for the same action (`open`, `new`, `list`, `check`, `export`); core returns the data (`outlineProject`, `checkProject` in `packages/core/src/project.ts`) and the CLI's wording is in the `cli` i18n area. A kind added later joins `list` and `check` there; its `FileMenu` items are its `export` formats once `commands.ts`'s `KIND_CLI` lists them, and so the MCP `export` tool's; a new command goes into `commands.ts` and gets both its CLI output and, when an agent needs it, an MCP tool, with a `pick` when one board, slide or tab has to be showing first. Files the editor hands the person go through `local.ts`'s `download`, so the command line can catch them. `new <kind> <name>` makes a folder of that name in the current directory and links it (a path works too; `--global` keeps the name in the projects folder; `.design/cli.md`). User docs: `docs/en/cli.md`.

Server events go through `apps/server/src/log.ts` (`DC_LOG_LEVEL`, `DC_LOG_FORMAT=json`), never bare `console.*`; a new fast-AI or delegation path logs its start and outcome there (`.design/server-log.md`).

End-to-end suites are listed in `docs/en/development.md` (one per kind, plus `launcher`, `dialogs`, `folders`, `git`, `theme`, `i18n`, `layers`, `embed`, `attach`, `import_here`, `import_board`, `run_feed`, `external_edit`, `tweak_text`, `template_values`, `theme_switch`, `chat_panel`, `side_resize`, `follow_up`, `fast`, `fast_slides`, `fast_motion`, `delegate`, `export_image`, `export`, `export_menu`, `image_gen`, `archive`, `claude_design`, `pptx`, `check_snapshots`, `baseline` (the editor's screenshots against the `e2e-baselines` branch; re-recorded by hand from the E2E patrol workflow)); add new suites to both language versions of that table, and to the `SUITES` table in `e2e/run.py` (`pnpm e2e`), which names what each suite needs started.

# Issues

A scheduled sweep every 5 hours runs `.claude/skills/issue-resolve/SKILL.md` over this repository's issues: team issues (owners, members, collaborators) go to analysis and a draft PR, external issues get one short evaluation comment and wait for a maintainer. Its stage lives in a hidden `<!-- issue-resolve stage=… -->` marker on its comments. Issues come in through the forms in `.github/ISSUE_TEMPLATE` (Feature / Bug / Feedback / Other plus an area); `issue-area.yml` turns the area into an `area/<name>` label and a `feat(motion):` title, and the sweep reads those labels. See `.design/issue-resolve.md`.

The homepage on GitHub Pages is `site/`, built and deployed by `.github/workflows/pages.yml`; the tingly-design-motion promo on it is rendered in CI by `scripts/build-site.sh`, not committed. See `.design/release.md`.

# Pull requests

Follow `.github/pull_request_template.md` (the same as Tingly Box's) for PR title and description. The title is `type(scope): what changed`. The description starts at `## Summary` with no header above it, then `## Key Changes`, within the template's length caps. Everything that is not about the change (requester, thread / session links, hidden markers) goes in a short, plain footer after a `---` rule; no badges, banners or "Generated with" lines.

- Screenshots go to the `pr-assets` branch, not into the feature branch.
- Say in the description which `.design/` note and which `CLAUDE.md` section the PR updated, or why none was needed.
