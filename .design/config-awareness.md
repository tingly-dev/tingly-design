# 配置变化：让 AI 能响应、能查到

状态：**方案**；第 1 期（§4.1 的配置事实）、第 2 期（§4.2 的跟进提议）和第 3 期（§4.3 里已有编辑入口的变化）已实施；速度和数据来源在编辑器里还没有手动入口，所以没有对应的提议。尺寸变化后的“让 Claude 重新排版”是已有的唯一一例，见 [size-adapt.md](./size-adapt.md)。

## 1. 问题

人手动改的东西（尺寸与比例、设计系统、动效的格式与速度、文档的外观……）大多不会触达 AI，有两处缺口：

1. **改了之后没人接话。** 人切换设计系统、改比例、加格式，页面按确定性规则跟着变（缩放、换变量），但“这一页现在该重新设计一下”这件事没有入口。已有的重排提示只管尺寸、只在比例大变时出现，且散在三个面板里各写一份（`SizeRows`、`MotionPanel`、幻灯片面板）。
2. **AI 查不到当前的关键配置。** `outline` 给了画板和格式的尺寸，但没有幻灯片尺寸、挂了哪些设计系统及其 tokens、动效的速度和帧率、看板的数据来源、文档的样式等。委托给 Claude Code 的请求只带最近 12 条改动摘要和当前选中，命令行、MCP 的智能体连这个都没有。AI 只能靠读文件猜，或者干脆不知道。

## 2. 约束

- **不自动跑。** 一次运行要花钱和时间，可能把人刚调好的东西改坏（见 [ux-principles.md](./ux-principles.md)：完成不等于锁死，副作用只在当前界面）。所以是“提议”，不是“触发”。
- **不新增模式选择器。** 提议出现在人正在做的地方，不另开一个“AI 联动”开关。
- **每种类型都要接上**（[project-kinds.md](./project-kinds.md)），不为画布单做。
- MCP 沿用“一步一个工具、没有模式参数”（见 [cli.md](./cli.md)），不为此新增写入类工具。

## 3. 可选做法

**响应变化**

| 做法 | 优点 | 缺点 |
|---|---|---|
| A. 改完自动让 Claude 跑 | 最省事 | 烧钱、改坏人刚调的东西、违背“不自动” |
| B. 每个面板各自放一个提示（现状推广） | 改动最小 | 文案和提示词散落，每加一种变化就要改每个面板；漏类型 |
| C. 共用的“跟进提议”：变化是数据，一张表决定提议什么，一个部件显示 | 一处接线，所有类型共用；提示词可预填、可改、可忽略 | 要定义变化的数据形态 |
| D. 只在对话里提醒，不放按钮 | 最轻 | 人要自己写提示词，等于没做 |

**让 AI 查配置**

| 做法 | 优点 | 缺点 |
|---|---|---|
| E. 新增 `settings` 工具 | 单独可查 | 多一步；`open` 已经是“进入项目并看概况”，两者重复 |
| F. `open` 的结果里加 `settings`（同一份数据也进每次委托的上下文） | 不新增工具，AI 一进来就有；委托运行不用额外调用 | 要控制体积 |
| G. 让 AI 自己读索引文件 | 零开发 | 各类型索引格式不同，AI 要先读技能才懂；设计系统 tokens 要拼 |

## 4. 决定

**C + F。**

### 4.1 配置事实（给 AI 看）

core 里加一张按类型的穷尽表 `SETTINGS: Record<ProjectKind, (files) => Settings>`，与 `OUTLINE`、`CHECK` 同级（漏了编译不过）。它只返回数据，不带措辞；体积上限是几百字，细节仍让 AI 去读文件。

| 类型 | 关键配置 |
|---|---|
| 画布 | 每块画板的尺寸，挂的设计系统，画板 `data-props` 的模板值名 |
| 幻灯片 | 页面尺寸（`deckSize`），挂的设计系统，分节 |
| 设计系统 | 主题名、颜色/字体 tokens 概要、有没有封面 |
| 看板 | 数据集及来源类型，页面文件 |
| 文档 | 标签页树、样式/外观（若有） |
| 动效 | 各格式尺寸，速度，帧率，总时长，是否有音频 |

出口：`open`（MCP、命令行 `list`/outline 的 JSON）的结果多一个 `settings`；`delegate.ts` 在“最近改动”之后追加一段 `Project settings:`，所以编辑器里的运行、命令行 `prompt`、MCP 的运行都一样看到。各类型技能（`.claude/skills/<kind>/SKILL.md`）加一句“设置在 `open` 的 `settings` 里，不要从文件里猜”。

### 4.2 变化与跟进提议

- **变化是数据。** 面板提交一次配置变化时，除了写文件，还记一条结构化的 `ConfigChange`：`{ type, scope, from, to }`，`type` 是闭集（`size`、`format-added`、`design-system`、`speed`……）。它同时是改动记录里的一行（动作者是人），所以刷新后还在、命令行 `history` 也能看到。
- **一张表决定提议什么。** core 的 `FOLLOW_UP: Record<ChangeType, (change, kind) => { reason, prompt } | null>`：返回 `null` 表示这种变化不值得提议（例如比例只变了 5%）。`needsRelayout` 的判断挪进这张表，尺寸只是其中一行。提示词是英文的模型请求，`reason`（给人看的一句话）走 i18n（`packages/i18n` 新区域或 `panel` 区域，中英文同时写）。
- **一个部件显示。** 共用的 `FollowUp` 取代三处各自的 `shifted` 提示：出现在请求栏上方一行（对话列模式在列里），文案是“尺寸改成了 1080×1920 · 让 Claude 重新排版”，三个动作：**发送**（带预填提示词，可先在请求栏里改）、**改写**（把提示词放进输入框，不发送）、**忽略**。提议不是弹窗，不挡操作。
- **何时消失。** 点了发送或忽略；或者之后又有同一范围的新变化（取代旧的）；或者人自己发的请求覆盖了它（见下一条）。待办的变化记在编辑器的状态里：每次 Claude 运行带走它们（见下一条），所以它们是“自上次运行以来”的变化。
- **自己写的请求也知道变化。** 不管人点没点提议，下一次委托运行的上下文里都会带“自上次运行以来的配置变化”（和 4.1 同一段），所以人直接说“把它弄好看点”时 AI 也知道尺寸刚变过。这条才是真正解决“AI 不知道”的，提议只是更省力的入口。
- **快速 AI 同样。** 快速 AI 的系统提示带 4.1 的精简版（只有尺寸和设计系统名），不带提议；提议默认走 Claude Code，因为重排、换风格是大改动，和 `size-adapt` 的做法一致。

### 4.3 各类型

| 类型 | 会产生的变化 | 提议的内容 | 结论 |
|---|---|---|---|
| 画布 | 画板尺寸；挂上/换设计系统 | 重排该画板；按新设计系统重画（只列受影响的画板） | 支持 |
| 幻灯片 | 页面尺寸；换设计系统 | 重排每一页；按新设计系统统一版式 | 支持 |
| 设计系统 | 改 tokens（色、字体、圆角……） | 检查用到它的组件，把用了硬编码值的地方改回变量 | 支持；用到它的项目在别处，提议只对设计系统自己的组件 |
| 看板 | 加/换数据来源 | 为新数据补图表和说明 | 支持 |
| 文档 | 换样式、增删标签页 | 统一样式、更新目录引用 | 外观设置还不多，先接尺寸以外的设计系统类变化；缺口记入矩阵 |
| 动效 | 新增格式；改速度 | 重排各场景的新格式覆盖；按新速度检查时间 | 支持，已有重排提示并入共用部件 |

AI 设置（模型、连接）的变化**不**产生提议：它不改项目内容。

## 5. 分期

1. core：`SETTINGS` 表、`open` 和委托上下文带上 `settings`；技能与 `delegate.ts` 的说明。无界面变化，可单独合并。
2. 把现有的重排提示换成 `FOLLOW_UP` 表和共用 `FollowUp` 部件，行为不变（只是同一件事不再写三遍）。需要界面截图和 `tingly-design-ui` 画布上请求栏一行的画板。
3. 加新的变化类型（设计系统、tokens、速度、数据来源），每种类型一个 e2e。

## 6. 未决

- 待办变化存在编辑器会话里（`recordChange`），不是从改动记录推出来的：刷新页面后提议和“自上次运行以来”的变化都没了。要不要写进改动记录让它跨刷新、跨窗口，取决于这条是否真的丢过信息；改动记录目前的摘要是给人看的文字，不是结构化数据。
- 同一个设计系统被多个项目挂着，改了 tokens 时，另一个项目里要不要也有提议？现在倾向不要（副作用只在当前界面），打开那个项目时再看差异。
- 同一件东西的连续改动合成一条（从最早的值到现在的值）：小步累加会触发提议，改回原样就没有变化。撤销（Ctrl-Z）还不会撤回这条记录，撤销后提议和“自上次运行以来”仍会说改过。
- 体积：设计系统 tokens 多时 `settings` 只给概要，细节要不要给一个按需读的 MCP 资源，待第一期实测。
