# Harness：怎么确认一切都还好用

状态：统一入口 `pnpm e2e`、三种节奏（巡检、发布前、PR 冒烟）、快照的版面检查、编辑器截图基线和跨类型矩阵的覆盖检查已实施。调研和考虑过的方向在 `.research/harness.md`。

## 问题

产品大部分是交互和画面，不是模型调用。单元测试管格式和写回，30 个 e2e 套件管交互，但 e2e 各有各的启动方式（有的要 `pnpm dev` 加 mock 模型，有的要不配模型的 `pnpm dev`，有的先 `pnpm build` 自己起服务，`embed` 要 `pnpm bundle`），没人一次跑全，坏了也没人知道。画面"对不对"更是没有任何检查。

## 决定

**先只做不依赖外部的部分。** 不调真实模型、不依赖 Tingly Box：mock 模型（`e2e/mock_anthropic.py`）和假的 `claude` 已经能覆盖要测的故障路径。真实模型的评测、视觉模型打分、VModel 编排、对外的 `verify` 命令都先不做。

**一个入口，按组起环境。** `e2e/run.py`（`pnpm e2e`）里有一张 `SUITES` 表，写每个套件属于哪一组；每组先起好它要的东西，组内逐个跑，跑完停掉。结果从套件打印的 `PASS` / `FAIL` 行读，不信退出码（很多套件失败时也退出 0），没有任何检查行或异常退出算 error，超时单独算。汇总写到 `e2e/out/report.md` 和 `report.json`，每个套件的输出在 `e2e/out/logs/`。

- 套件会改示例项目再 `git checkout` 回去，所以 `projects/` 有未提交改动、或有一个只剩被忽略文件的文件夹（上一次留下的改动记录）时不开跑，`--force` 例外。不这样做，会悄悄丢掉人的改动，或者让"导入后取一个空闲的名字"这类检查拿到 `-3`。
- 每组用临时的 `DC_CONFIG`，不读这台机器上存的模型设置。
- `DC_CHROME` 没设时用 Playwright 的无头版（完整版 Chromium 无头时点缩放后的画板会点偏）。
- `delegate` 调真实的 `claude`，只在 `--real` 时跑。

**全量 e2e 不进每个 PR。** 整套大约十分钟，还要装浏览器、起几轮服务，每个 PR 都跑代价太大。分三种节奏（`.github/workflows/e2e.yml`）：

| 节奏 | 跑什么 | 红了怎样 |
|---|---|---|
| 巡检：每晚在 main 上，也可手动触发 | 全量 | 开一个 `e2e-patrol` 标签的 issue（已有就追加评论），转绿后自动关；不拦合并 |
| 发布前：`release.yml` 打包前调用 | 全量 | 拦住发布 |
| PR 冒烟：改了 `apps/`、`packages/`、`e2e/`、`projects/` 时 | `--smoke`：每种类型一个套件，加运行反馈 | PR 上一个红的检查 |

冒烟集合是 `run.py` 的 `SMOKE`，选的是"打开、编辑、写回"最直接的那个套件，加上 `run_feed`（请求栏在六种类型里都有一次运行）。

报告和日志作为 `e2e-report` 产物上传，`report.md` 也写进运行页的摘要。

**快照看版面，不只看画没画出来。** `check --snapshots` 每画一项，就在当时显示着的每个作品框架（画板、幻灯片、看板页面、组件预览）里跑一段探针（`apps/server/src/layoutProbe.ts`），看浏览器实际排出来的版面：

| 规则 | 什么时候报 | 为什么这样定 |
|---|---|---|
| `clipped` | 有自己文字的元素 `overflow` 是 hidden / clip，内容比框大，且没用省略号或行数截断 | 有意截断会写省略号；没写就是放不下 |
| `outside` | 文字跑出框架边缘；只对画板和幻灯片 | 这两种是固定尺寸，出界就看不见了；看板和设计系统视图会滚动，不算 |
| `contrast` | 文字和它身后第一块不透明的纯色背景对比度低于 WCAG AA（普通字 4.5:1，大字 3:1） | 用公认的线；背后是图片、渐变或半透明层时没有单一颜色可比，不判 |
| `blank` | 框架里既没有文字，也没有图片、SVG、画布、嵌入，也没有比框架小的色块 | 铺满整个框架的颜色只是背景 |

都是警告，不是错误：设计里可能有意裁字、有意用淡色的说明，检查器分不出来。对比度不够的往往成批出现（一块画板上所有的灰色注释），所以按文件合成一行：几处、最低多少、举一个例子（`contrastMany`），不然一个线框图项目能报出上百条，没人会看。探针是一段纯 JavaScript 字符串，不走打包，免得构建工具往函数里插东西后在框架里跑不起来。动效走 `render.ts` 的精确渲染，不经过这些框架，暂时不查。

**编辑器自己的样子用截图基线管。** 版面探针看的是作品，编辑器的外壳（启动页、顶栏、面板、明暗主题、中文排版）改坏了它看不出来。`e2e/baseline.py` 给启动页和六种类型的示例各截一张，明暗 × 中英共 28 张，和 `e2e-baselines` 分支上的同名截图比：

- 固定 1440×900、减少动效、关掉动画和过渡、等 2.5 秒再截，同一台机器连跑两次 28 张全同。
- 一个像素任一通道差超过 24 才算变了，一张图变了的像素超过 0.2% 才算不同：抗锯齿和字体微调会挪动零星像素，真改了界面动的远不止这些。不同的那张和一张标红的差异图留在 `e2e/out/baseline/`，跟着 `e2e-report` 上传。
- 还没有基线的截图算过，并写明"no baseline yet"，所以第一次录之前不会把巡检弄红。
- **不自动接受。** 截图变了巡检就红；人看过差异图、确认是有意的，再手动运行 E2E workflow 勾上 "record baselines"，它在同样的 runner 上重截、推到分支（`.github/scripts/e2e-baselines-push.sh`）。基线依赖机器的字体和 Chromium 版本，所以在哪儿比就在哪儿录，不从开发机录。
- 基线放在只有图片、和 main 没有共同历史的旁路分支上，不让主分支每次改界面都背几兆图片。
- 只在巡检和发布前跑，不进 PR 冒烟：一个改了界面的 PR 在合并前没法有对的基线。

**跨类型矩阵的每个 ✓ 都要说清谁在测。** `.design/project-kinds.md` §3 说某功能在某类型里支持，过去没有任何东西对得上测试。`e2e/coverage.json` 按"功能 → 类型"写：一组套件名，或者一句为什么还没有套件测它。`scripts/check-coverage.mjs`（`pnpm test` 的最后一步）读矩阵本身，查三件事：每个 ✓ 格子在数据里都有一项；数据里的每项在矩阵里都是 ✓（矩阵改了、数据没跟上会报出来）；写到的套件都在 `run.py` 的 `SUITES` 里。

- 功能名取矩阵第一列"（"之前的部分，所以矩阵还是人写的那张表，不另起一份数据源；改行名要一起改数据。
- 没测的格子允许存在，但必须写原因：这样缺口是看得见的一张清单，而不是默认"大概测过"。
- 只查"有没有套件声称覆盖"，不查套件里是不是真的点到了那个类型；后者要靠读套件，代价和收益不成比例。

## 没定的

- PR 冒烟要不要设成必过检查（仓库设置，不在这里决定）。
- 冒烟集合的大小：等巡检跑出几次真实耗时再调。
