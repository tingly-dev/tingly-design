# AI 编辑的渐进上屏

状态：**已实施**（沙箱画框对每一次更新做增量调和，不再整板重挂；输入侧的逐条到达本来就有）。还保持整块刷新的地方和原因见 §4；"还开着的问题"是没做的。

## 1. 问题

用户要求：AI（快速 AI、Claude Code）编辑过程要逐步可视化，能渐进的尽可能渐进，而不是等整次编辑完成后一次性刷新。

把从模型输出到画布渲染的链路捋一遍后，结论是：**输入侧早就是渐进的，缺的是渲染侧**。

- 快速 AI：回复流式到达，每条 jQuery 语句一完成就在隐藏执行器里跑一次，画板立即以草稿（虚线框）显示（`fastedit.ts` 的 `runOne` → `setDraft`）。
- Claude Code：`claude` 直接写项目文件，chokidar 监视器（60 ms 稳定窗）每个写盘发一个 SSE `file` 事件（actor 记为 `claude`），编辑器 `onEvent` 立刻替换 `files[path].server`，运行结束只做记录，不刷新。
- 看板：数据文件、数据集的变化本来就是定点刷新（`dash.ts`），只有页面文件变化整页重载（250 ms 防抖）。

但两条链路的每一次更新落到画框上都走同一个出口：`runtime.tsx` 里 `<DcComponent key={current.source}>` 以整份源码为 key，模板的类缓存也按整份源码建类——于是**每改一个字，整块画板卸载重建**：图片重新加载、`<x-embed>` 内嵌框重开、播放中的构建动画重放、正在读的内容闪一下。一次 Claude Code 运行改 N 次同一文件就是 N 次整板重挂，"渐进"被渲染侧的闪烁吃掉了。

## 2. 决定：渲染侧做增量调和（`packages/sandbox`）

沙箱运行时把"整份源码"当身份改成"每一步改了什么就补什么"，两处配合：

1. **类按脚本缓存，不按源码**（`template.tsx` 的 `compile`）：缓存键从 `file\0source` 改成 `file\0script`。页面的脚本（`class Component extends DCLogic`）没变而标记变了——渐进编辑的每一步都是这样——就复用同一个类，React 把新标记调和到已画好的 DOM 上；类自己的 render 从 `__dcSource` prop 读当前标记。脚本变了是换了页面程序，新类自然重挂，和从前一样。
2. **兄弟节点按开标签记名**（`renderNodes`）：每个兄弟的 key 是它**自己的开标签**（标签加属性，不含子节点）的短哈希，相同开标签的兄弟（列表行、同款卡片）加序号按位置配对。开标签不变就视作同一个元素实例：改文字、改样式是原地补丁；在深层加删部件时，祖先的开标签没变，从根到改动点的整条路径都原地不动——若按整个子树切片记名，任何深层改动都会换掉所有祖先的 key，把整板重新挂一遍，渐进就名存实亡。改标签名（换元素类型）才重挂。

这条格式自己的规则保证了第 1 点的安全：skill 和委托提示都写明"UI 全部写在 `<x-dc>` 标记里，脚本不许建 DOM"，脚本是 props 的纯函数（`renderVals()`），类可以跨源码复用。脚本里持有的 React 状态在纯标记编辑之间延续，页面不闪不重置，比原来的每次重挂更贴近"正在编辑的同一页"。

**最终一致**：调和的目标树就是最终源码的目标树，React 提交后的 DOM 与一次性渲染最终源码相同；`data-dc-tid`、选中框、检查器读的是提交后的 DOM，照旧成立。不渐进的路径（模式切换、文字提交收尾的 `renderKey` 重挂）保持原样。

验证：单测、typecheck、knip/depcheck，以及 e2e 的 `fast`、`fast_slides`、`fast_motion`（流式语句逐条上屏）、`external_edit`（写盘 → 监视器 → 画框）、`e2e`、`slides`、`motion`、`tweak_text`、`layers`、`template_values`、`ds`、`dash`、`docs`、`copy_png`、`run_feed`、`theme_switch`、`embed`（bundle 生产构建）；另用 Playwright 探针直接驱动真实编辑器：对一块画板连做改字、插入兄弟、连续六次快速写盘，前后的 DOM 节点是同一个（`isConnected` 且引用不变）、新内容出现、最终态正确。

## 3. 输入侧不再加东西

- **逐句/逐写盘就是合适的粒度**：Claude Code 的 Edit 工具一次写一个完整文件，没有半个文件的中间态可流；60 ms 稳定窗之后立即推送，编辑器不再加防抖——加了只会推迟看到，不会更渐进。
- **快速 AI 的草稿不落盘**：存盘仍是回复结束时的普通一次编辑（冲突时整份语句列表在新版本上重放）。逐句存盘会把日志和版本历史淹没在中间态里，也破坏"一次回复一个撤销步"。多观察者实时看到别人页面上的草稿需要服务端另立草稿通道，见 §5。

## 4. 仍然整块刷新的，和为什么

- **看板页面文件变化 → 整页重载**（250 ms 防抖）：看板页是一段自己跑的脚本加 d3，没有声明式的元素树可调和；定点刷新只做得到数据层。
- **`<x-embed>` 的标记变了 → 内嵌框重开**（`slide.tsx` 里 iframe `key={html}`）：内嵌页的 CSP 允许行内脚本，标记更新必须在一份新文档里重新执行它们；标记没变的内嵌框在调和下保持不动。
- **快速 AI 的重试轮**：某一轮回复错了就整份作废，从请求开始时的版本重来——错误的状态不该渐进保留。

## 5. 还开着的问题

- **多窗口 / 多观察者的实时草稿**：快速 AI 的草稿只在发起编辑的浏览器里可见（存的是编辑器 store 的 `drafts`）；别人要看同一个画板的逐句变化，得等那次保存。要做成直播需要服务端的草稿通道和冲突语义，等有人这么用再做。
- **语句间的过渡动画**：现在是"下一步出现"，没有补间；给新元素加进入动画容易变成视觉噪声，先不做。
