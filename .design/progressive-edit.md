# AI 编辑的渐进上屏

状态：**已实施**（沙箱画框对每一次更新做增量调和，不再整板重挂；输入侧的逐条到达本来就有，委托提示再劝模型分笔落盘；必须整页重载的看板页面和设计系统预览用双帧交接遮住白屏）。还保持整块刷新的地方和原因见 §5；"还开着的问题"（§6）是没做的。

## 1. 问题

用户要求：AI（快速 AI、Claude Code）编辑过程要逐步可视化，能渐进的尽可能渐进，而不是等整次编辑完成后一次性刷新。

把从模型输出到画布渲染的链路捋一遍后，结论是：**输入侧早就是渐进的，缺的是渲染侧**。

- 快速 AI：回复流式到达，每条 jQuery 语句一完成就在隐藏执行器里跑一次，画板立即以草稿（虚线框）显示（`fastedit.ts` 的 `runOne` → `setDraft`）。
- Claude Code：`claude` 直接写项目文件，chokidar 监视器（60 ms 稳定窗）每个写盘发一个 SSE `file` 事件（actor 记为 `claude`），编辑器 `onEvent` 立刻替换 `files[path].server`，运行结束只做记录，不刷新。
- 看板：数据文件、数据集的变化本来就是定点刷新（`dash.ts`），只有页面文件变化整页重载（250 ms 防抖）。

但两条链路的每一次更新落到画框上都走同一个出口：`runtime.tsx` 里 `<DcComponent key={current.source}>` 以整份源码为 key，模板的类缓存也按整份源码建类——于是**每改一个字，整块画板卸载重建**：图片重新加载、`<x-embed>` 内嵌框重开、播放中的构建动画重放、正在读的内容闪一下。一次 Claude Code 运行改 N 次同一文件就是 N 次整板重挂，"渐进"被渲染侧的闪烁吃掉了。

看板页面和设计系统组件预览不走沙箱画框：它们各自是一个整页 iframe，文件一变就重载，白一下。Claude 改几笔就白几次，渐进被白屏吃掉。这两处的处理见 §4。

## 2. 决定：渲染侧做增量调和（`packages/sandbox`）

沙箱运行时把"整份源码"当身份改成"每一步改了什么就补什么"，两处配合：

1. **类按脚本缓存，不按源码**（`template.tsx` 的 `compile`）：缓存键从 `file\0source` 改成 `file\0script`。页面的脚本（`class Component extends DCLogic`）没变而标记变了——渐进编辑的每一步都是这样——就复用同一个类，React 把新标记调和到已画好的 DOM 上；类自己的 render 从 `__dcSource` prop 读当前标记。脚本变了是换了页面程序，新类自然重挂，和从前一样。
2. **兄弟节点按开标签记名**（`renderNodes`）：每个兄弟的 key 是它**自己的开标签**（标签加属性，不含子节点）的短哈希，相同开标签的兄弟（列表行、同款卡片）加序号按位置配对。开标签不变就视作同一个元素实例：改文字、改样式是原地补丁；在深层加删部件时，祖先的开标签没变，从根到改动点的整条路径都原地不动——若按整个子树切片记名，任何深层改动都会换掉所有祖先的 key，把整板重新挂一遍，渐进就名存实亡。改标签名（换元素类型）才重挂。

这条格式自己的规则保证了第 1 点的安全：skill 和委托提示都写明"UI 全部写在 `<x-dc>` 标记里，脚本不许建 DOM"，脚本是 props 的纯函数（`renderVals()`），类可以跨源码复用。脚本里持有的 React 状态在纯标记编辑之间延续，页面不闪不重置，比原来的每次重挂更贴近"正在编辑的同一页"。

**最终一致**：调和的目标树就是最终源码的目标树，React 提交后的 DOM 与一次性渲染最终源码相同；`data-dc-tid`、选中框、检查器读的是提交后的 DOM，照旧成立。不渐进的路径（模式切换、文字提交收尾的 `renderKey` 重挂）保持原样。

验证：`external_edit` 套件在画板、幻灯片和动效场景里给每个已画出的元素打上标记，再依次改深层文字、在前面插入兄弟、连续快速写盘，每一步之后标记都还在——节点没有被重建；其余沿用各类型已有的套件（`fast*` 流式上屏、`e2e`、`slides`、`motion`、`embed` 等）。实际 Chrome 里的渲染以套件为准，没有为此另做单测（沙箱包没有 DOM 测试环境）。

## 3. 输入侧：粒度已经合适，只补一句提示

- **逐句/逐写盘就是合适的粒度**：Claude Code 的 Edit 工具一次写一个完整文件，没有半个文件的中间态可流；60 ms 稳定窗之后立即推送，编辑器不再加防抖——加了只会推迟看到，不会更渐进。
- **快速 AI 的草稿不落盘**：存盘仍是回复结束时的普通一次编辑（冲突时整份语句列表在新版本上重放）。逐句存盘会把日志和版本历史淹没在中间态里，也破坏"一次回复一个撤销步"。多观察者实时看到别人页面上的草稿需要服务端另立草稿通道，见 §6。
- **委托系统提示劝模型分笔落盘**（`delegate.ts` 的 `STEPWISE`，六种类型共用一句，接在标点规则后面）：一次 Edit / Write 对编辑器是一个原子事件，事件内部无法再流式，能拆的只有"几次工具调用"。所以对模型提要求：大改动尽量分几笔写，每笔都让作品完整地显示（一节、一张卡、页面的一部分），除非改动必须整体成立（改名、重排到一半会坏的那类）。劝而不强制：每多一笔就是一次模型往返，是否分、分多细由模型按改动性质权衡，不把"渐进"做成固定的耗时开销。

## 4. 必须整页重载的表面：双帧交接

看板页面是一段自己画 DOM 的脚本（d3 等），设计系统预览是一份按 bundle 现编的文档；两者都没有可调和的元素树，换内容就是换一份新文档。能做的是不让人看见换的过程：两个 iframe 轮流，台上的留着，下一版在隐藏的孪生帧里启动，等它真的画好了再交换位置。

- **看板页面帧**（`DashApp.tsx` 的 `PageFrame`）：孪生帧每次都是全新的帧，页面脚本的 window 环境干净，不会叠监听器；等它 `dash-declared`（页面挂载完）再上台，5 秒兜底，页面挂不完也接管。两个约定使数据不断：
  - 页面在挂载途中（`dash-declared` 之前）就会 `dash-want` 要数据，所以"我们对哪一帧说话"（`frameWin`）在孪生帧 `ready` 时就切过去，答复由缓存供给；`dash-want` 台上和启动中的帧都听，退场帧的不听。
  - 除此之外只有台上的帧说话算数（`dash-refresh`、`dash-report`、`dash-pick`……都按发送帧过滤）。交换时清空旧页面的报告（`.runs.json` 由新页面重画后重新报告）。
  
  两个容易漏的情形：台上的帧自己重载（界面语言变了，`srcdoc` 随语言变，两个帧都重载）时，它重新发 `ready`，必须像孪生帧一样把页面文件、数据集、参数、主题再发一遍，否则页面永远空白；换下台的旧帧要卸载而不是只换 class，否则它的脚本（定时器、轮询）继续跑，还在发请求。
- **设计系统组件预览**（`ComponentViews.tsx` 的 `Preview`）：bundle.js / bundle.css / tokens.json 每笔写入原来都让每个预览 iframe 重载一遍。同样两帧轮流，孪生帧 `onLoad` 后接管、旧帧退场；高度消息只听台上帧，免得启动中的帧把卡片高度顶来顶去。孪生帧加载期间文档又变回台上这份时，孪生帧丢弃（否则它加载完会把过期的版本顶上台，再被纠正回来，人看到一次闪回）；加载完时它的文档已不是当前文档的，也不上台。
- 共同的教训：两帧的 React key 必须带槽位名，否则第 2 次启动时两帧同号，React 调和错元素。

## 5. 仍然整块刷新的，和为什么

- **看板页面文件变化 → 整页重载**（250 ms 防抖）：重跑页面脚本就是它的契约，没有声明式的元素树可调和；定点刷新只做得到数据层。§4 的双帧交接把重跑时的白屏藏掉了，不是少跑。
- **`<x-embed>` 的标记变了 → 内嵌框重开**（`slide.tsx` 里 iframe `key={html}`）：内嵌页的 CSP 允许行内脚本，标记更新必须在一份新文档里重新执行它们；标记没变的内嵌框在调和下保持不动。
- **动效的播放器帧**（`motion.ts`）：把整段作品画成一份静态 DOM 供逐帧 seek，作品变了就整体重建；它在编辑时被隐藏，舞台上可编辑的那一场（和画板、幻灯片同一个运行时）是增量的。
- **快速 AI 的重试轮**：某一轮回复错了就整份作废，从请求开始时的版本重来——错误的状态不该渐进保留。
- **一次写入的内部**：内容在模型一侧就完整了，写入前无从流式；"逐元素"只能靠 §3 的分笔提示拆成多次工具调用。

## 6. 还开着的问题

- **多窗口 / 多观察者的实时草稿**：快速 AI 的草稿只在发起编辑的浏览器里可见（存的是编辑器 store 的 `drafts`）；别人要看同一个画板的逐句变化，得等那次保存。要做成直播需要服务端的草稿通道和冲突语义，等有人这么用再做。
- **语句间的过渡动画**：现在是"下一步出现"，没有补间；给新元素加进入动画容易变成视觉噪声，先不做。
