# 自身设计稿：用 Tingly Design 画 Tingly Design

状态：**已实施**（画布 `projects/tingly-design-ui`）；§5 是还开着的问题。

## 1. 问题

编辑器的界面散在六种类型、几十个组件里。要回答"请求栏在看板里长什么样""文档的右侧面板放什么""这个新按钮该放哪"，只能打开六个项目一个个看，或者读代码。改一处界面时，也没有一个地方能先把改动画出来、和其他类型放在一起比。

Tingly Design 本身就是做界面设计稿的工具，所以设计稿就用它自己画：一个画布项目，画编辑器自己的结构。

## 2. 考虑过的做法

| 做法 | 好处 | 问题 |
|---|---|---|
| 截图集（`docs/` 或 PR 附件） | 和实际一模一样 | 只能看不能改；说不清"为什么在这里"；改一个想法要先改代码 |
| 外部设计工具（Figma 等） | 设计师熟悉 | 和仓库分开，代码改了没人同步；Claude Code 改不到 |
| **仓库里的一个画布项目** | 文件在 git 里，随 PR 一起改；人在画布上改，Claude Code 直接写文件；本身就是这个产品的用例 | 是线框而非像素级还原，需要约定画到什么程度 |

选了第三种。

## 3. 画什么、画到什么程度

画布按"一个人会问的问题"分区，每一行一个标题：

- **整体怎么拼起来**（`Map`）：启动页 → 编辑器外壳（顶栏、左侧列表、工作区、浮动工具栏）→ 右侧面板、请求栏、菜单、AI 模型设置。旁边是主题 token（`Tokens`），画板都用浅色 token 画。
- **每种类型共用的框**（`Shell`、`Launcher`）：外壳的七个区域，以及一张表：六种类型各用了哪些区域（左侧列表、工具栏、右侧面板的标签、请求栏的目标）。
- **顶栏和菜单**（`Main`、`Kinds`、`Menus`）：顶栏的三段，六种类型的顶栏并排，项目菜单、导入 / 导出、"更多"、AI 模型设置。
- **六种类型**（`Canvas`、`Slides`、`DesignSystem`、`Dashboard`、`Doc`、`Motion`）：每块板左边是 1280×800 的界面线框，上面用橙色编号标出区域；右边是同号的说明，最后一个黄色框是这一类还开着的问题。
- **请求栏**（`AgentBar`）：底部的空闲、运行中、完成、折起四种状态，停靠右侧时的隐藏、探出两种状态，以及方案中的钉在左侧（对话记录、位置菜单、窄带、窄窗口退回，见 [chat-panel.md](./chat-panel.md)）。

画到什么程度：

- **结构和措辞准确，细节用线框**。区域、顺序、按钮、面板标签、真实的界面文案要和代码一致；作品内容（画板里的东西、幻灯片正文、图表数据）用灰条或 `[n]`、`[name]` 这样的占位，不编数字。
- **颜色只用编辑器的 token 值**，这样画板上看到的层次就是编辑器的层次。
- **画板是普通 `.dc.html`**：样式写在行内、文字直接写在标记里，可以在画布上点选、改字、拖动；不用脚本生成 DOM。

## 4. 怎么维护

- **先画再改代码**。改任何人看得见的编辑器界面之前，先在对应的画板上改（或者新增一块板），和其他类型放在一起看过再动代码。
- **代码变了，同一个 PR 里重画**。画布是"现在的样子 + 要改成的样子"，不是历史；代码已经和画板不一样时，以代码为准，把画板改回来。
- **差异写成问题**。画的过程中发现的不一致（例如设计系统顶栏的导入 / 导出还是文字链接），写进那块板的黄色"Open"框，而不是悄悄画成理想状态。
- **新类型、新的跨类型功能**：按 [project-kinds.md](./project-kinds.md) 登记之外，在这里加一块类型板，并在 `Shell` 的表里加一行。

## 5. 还开着的问题

各类型板上的黄色框是界面本身的问题（页面选择器放哪、幻灯片缺缩放、文档的格式栏、看板的两个"月亮"、设计系统的导入 / 导出写法和主题选择器、请求栏在没有目标的类型里不给快速 AI）。这份说明只记设计稿本身的问题：

- **深色和中文**：画板只画了浅色、英文。深色由 token 推得出来；中文会改变宽度（顶栏、面板标签），重要的地方是否要并排画中文，还没定。
- **窄屏**：顶栏在 900 px 以下怎么收，`Main` 里写了是开放问题，还没画。
- **和代码对照**：现在靠人对照截图。可以加一个检查：把每种类型实际截图和画板放在同一张图里，PR 里一眼看出差异。
