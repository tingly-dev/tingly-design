# 跳回早先的阶段（stages）

状态：**已实施**。测试在 `e2e/git.py`（提交套件里一并覆盖）。问题来源：[issue #420](https://github.com/tingly-dev/tingly-design/issues/420)。

## 1. 要解决的问题

项目可以一路改下去，但没有一个"回到早先某个状态"的动作。改动能被看见：改动记录（journal）一行行记着谁改了什么；git 存着从改动记录里做的提交；docs 的标签页另有 `.history/` 快照（[docs-history.md](./docs-history.md)）。可是：

- journal 存的是摘要，不是内容——`JournalEntry.version` 是写入后的版本号，不是可恢复的指针；
- git 只有提交（`initRepo`、`commitFolder`、`gitState`），没有列出、没有恢复；
- 编辑器的撤销栈在内存里，重开项目就清空。

所以一小时前发现某轮改动改坏了，只能离开编辑器去终端里开 git。相关但更窄的既有工作：#258（撤销较早的一轮对话）、#266/#267（只有 docs 标签页的版本）。

## 2. 选过的办法

| 问题 | 选项 | 结论 |
|---|---|---|
| 阶段是什么 | A journal 的一行；B 一次 git 提交；C 另存一套项目级快照（`.history/` 的项目版） | **B**。A 没有内容，恢复无从谈起；C 要自己管空间和清理，和"提交到 git"重复——git 已有内容寻存，提交按钮就在改动记录里。B 的代价是要有仓库：没仓库时引导第一次提交，沿用 [project-git.md](./project-git.md) 的"第一次提交时建仓库"，问题自然消失 |
| 恢复方式 | A 硬重置（`reset --hard`，工作区直接变成旧阶段）；B 只进不退的前向恢复（把旧阶段的内容当**一批新改动**写回来） | **B**。A 会扔掉未提交的工作且在 git 层面不可撤销；B 之后当前状态还在编辑器撤销里，跳回本身也记入日志，时间线保持诚实，历史一条线不转弯 |
| 跳回的撤销 | A 恢复前自动建一个"保险提交"；B 编辑器内存撤销（toast 带 Undo） | **B**。自动提交侵入太强，打断人自己的提交节奏；文本文件的跳回在编辑器里整批可撤销。二进制资产不参与撤销，见"没定的" |
| 范围 | A 按文件/按类型单独回退；B 整个项目文件夹 | **B**。阶段的定义就是整个项目的快照；按文件回退是 docs 的 `.history/` 已经做的事 |
| 入口 | A 项目菜单；B 改动记录弹层加一页 | **B**。改动记录已经是历史面（六种类型同一个 `JournalPopover`），提交按钮也在那里；"看历史"和"回到历史"是同一个问题的两面 |

## 3. 决定

| 问题 | 决定 | 为什么 |
|---|---|---|
| 列出阶段 | `GET /api/projects/:p/git/stages`：项目文件夹里 `git log -n 50 --format=%h%cI%s -- .`，新的在前；没有仓库或还没有提交时返回空表，弹层给提示 | 只列这个项目文件夹的提交；项目在别人的仓库里时，别人的提交不混进来 |
| 恢复 | `POST /api/projects/:p/git/restore` `{stage}`，在项目锁里：读阶段树（`git ls-tree -r`）和工作区清单（`git ls-files -co --exclude-standard`，再手工排除本机文件），算出差——阶段有而工作区无或内容不同的**文本**文件走 `writeAtomic` 写回并 `publish` file 事件，阶段没有而工作区有的删除（`removeFile`）并 publish delete 事件；二进制资产（assets、fonts、ds、data、uploads 下的）原样写回，不产生 file 事件 | 恢复不跑任何 git 写命令，只读旧树；`writeAtomic`/`removeFile` 记入 `ownWrites`，文件监视器不会把恢复当成外部改动再记一遍；打开着的编辑器经 SSE 即时看到恢复后的内容 |
| 日志 | 记**一条** `{actor:'human', file:<短哈希>, summary:'restored stage <哈希> <提交说明>'}` | 逐文件记录会和改动记录里本来就有的每行变化重复；一条记录说明"这里跳回过"，时间线保持诚实 |
| 与 Claude Code 并发 | 有委托正在跑（`activeDelegates`）时拒绝，报错等它结束 | 恢复写到一半和 Claude 的写交错，两边的"之前/之后"都不再可信 |
| 本机文件 | `.journal.jsonl`、`.runs.json`、`.claude-session.json`、`.transcript.jsonl`、`.image.json`、`.references.json`、`renders/`、`.history/` 从不进入恢复（LOCAL 清单同 [project-git.md](./project-git.md)） | 它们只属于这台机器 |
| 入口 | `JournalPopover` 顶部一个双段开关（改动 \| 阶段）。阶段页没有仓库时提示先提交（提交按钮就在页头）；每行是说明、时间、短哈希，动作"跳回" | 第 2 条：直接进工作面，不先选模式；第 3 条：改动词与"阶段"分开，一个词一个义 |
| 确认 | 确认框先问服务端真实要执行的差，说"会写回 n 个文件、移除 m 个文件"，再说明只进不退、可用 Undo | 第 7 条：诊断走真实路径，数字就是将要执行的差 |
| 撤销 | 服务端返回每个文本文件的 before/after；编辑器把它们组成一个撤销批次（toast 带 Undo）：被改的整文件换回 before（`edit`，actor `undo`）、被移除的 `putFiles` 写回、恢复新出现的 `deleteFile` 删掉；二进制不参与 | 第 10 条：完成 ≠ 锁死。批量撤销沿用每轮运行整体撤销（`undoDelegate`）的办法 |
| 不自动提交 | 跳回之后工作区的改动数增加，人自己决定何时提交 | 恢复不碰 git 历史；要把"跳回前的状态"也留成阶段，得先提交——确认框里说清楚 |

## 4. 没定的

- 没有仓库时的项目级快照不做：阶段锚定在提交上，第一次提交把仓库建起来后这个缺口消失。
- CLI 的 `history` 和 MCP 没有 restore，编辑器先行，需要时再把同一对路由接过去。
- 阶段列表没有内容预览（哪些文件会动只在确认框给数字）；#417 给 docs 做的块级对比可以搬到阶段上。
- 二进制资产的跳回不可撤销：资产不进编辑器的撤销引擎；跳回前有未提交的资产改动时要靠人先提交。
- 两个窗口同时开着：恢复走项目锁，另一个窗口经 SSE 走外部改动同一条路径，没有冲突处理（同 [chat-panel.md](./chat-panel.md) §7 的既有答案）。
