# 导入外部素材（HTML、Markdown、PPT）：调研与评估

状态：**HTML、SVG → 画布已实施**（`packages/import`，见 §10、§11），Figma、HTML 幻灯片、Markdown 和 PPT 仍是评估。本文回答一个问题：用户手里已经有别处做好的素材（一个 HTML 页面、一份 Markdown、一套 PPT），怎样把它变成 tingly-design 里可以双向编辑的项目，值不值得做，先做什么。路径相对本仓库。

## 0. 结论先说

- **值得做，HTML 先做，判断是对的。** 但"能打开"和"能双向编辑"是两回事。把 HTML 原样塞进 `.dc.html` 已经能渲染、能选中、能改字、改色，回写也只动一行（§2.3 的实测）；真正的工作量在于**把它整理成编辑器擅长编辑的形状**：样式内联、文字是字面量、布局是 flex/grid + gap、一个画板一块内容。
- **推荐路线：确定性转换打底，AI 整理为可选的第二步，截图比对兜底。**
  1. 在浏览器里真实渲染导入的页面，读出计算后的样式，生成内联样式的 `.dc.html`（不靠模型，快、可重复、保真度高）；
  2. 再让 Claude Code 按 `dc-canvas` 规范把它"整理"成干净的 flex/grid 结构（可选，按画板做，人可以对比后接受）；
  3. 每一步都和原页面截图做像素比对，把差异和丢掉的东西（脚本、悬停态、媒体查询）列成一份导入报告。
- **Markdown → 文档几乎是现成的**（文档本来就存 Markdown），1～2 天，可以和 HTML 一起做。
- **PPT → 幻灯片是另一个量级**：要自己解析 PPTX 的 DrawingML，而幻灯片格式是封闭子集，形状、图表、主题都要映射或降级。放在第三阶段，先出"文字和图片都能改、版式靠绝对定位"的版本。
- 建议先做 **第一阶段（HTML 单页 → 画布，约 1.5～2 周）+ Markdown 导入**，看用户真实素材的效果再决定后面。工作量是按现有代码推算的估计，不是实测。

## 1. 现在的"双向编辑"靠什么

双向的意思是：画布上的每个操作都能落到源码里**唯一确定的一处**，源码的任何改动也能立刻反映到画布上。做到这一点靠的不是解析器多聪明，而是**文件本身受约束**：

| 类型 | 文件 | 约束（让操作有唯一落点） | 回写方式 |
|---|---|---|---|
| 画布 | `canvas.json` + `*.dc.html` | 模板在 `<x-dc>` 里；视觉属性写在内联 `style`；文案是字面量；布局用 flex/grid + `gap`；脚本只在 `data-dc-script` 的 `DCLogic` 类里 | `packages/core/src/copy.ts`：parse5 带源码位置解析，改动只替换变了的属性/文字/子节点区间 |
| 幻灯片 | `deck.json` + `slides/<id>.html` | 更严：1920×1080、一个 `<section>`、封闭的标签与 CSS 子集（`packages/core/src/slides.ts` 检查，不阻止保存） | 同上 |
| 文档 | `doc.json` + `tabs/<id>.md` | GFM 子集（标题、列表、表格、代码块、图片…），原始 HTML 不可编辑 | `packages/core/src/docs.ts` 的 `mergeBlocks`：按块、块内按行合并，没变的块保持原文 |
| 设计系统 | `tokens.json` 等 | token 族的固定语法 | JSON |
| 看板 | `dash.json` + `datasets/` + `files/index.html` | 数字必须带 `data-source` 标注 | 文件 |

几个容易忽略的细节，都会直接影响导入：

- **属性面板读写的是内联 `style`。** 元素没写内联样式时，面板把计算值显示成占位（`apps/editor/src/components/panel/fields.tsx`），一改就写成内联覆盖。所以 class 写的样式"能改"，但源码里会出现内联与 class 两套并存。
- **模板里的 `{{…}}` 一律当作插值。** 外部页面里正文出现 `{{name}}`（Vue/Handlebars 模板、代码示例）会被渲染成空。字符串字面量是支持的（`packages/sandbox/src/runtime.tsx` 的 `lookup`），所以导入时可以把字面的 `{{` 写成 `{{ '{{' }}` 规避，不必改运行时。
- **脚本和字符串事件不会执行。** 模板里的 `<script>` 渲染为空，`onclick="alert(1)"` 这种字符串处理器被丢弃，事件只认绑定到 `DCLogic` 函数的 `onClick="{{fn}}"`。
- **画板沙箱禁网络。** 画板 CSP 只放行 Google Fonts 的样式和字体、任意图片（`packages/core/src/protocol.ts` 的 `cspFor`）。外链 CSS、外链脚本、自托管字体都加载不了，必须在导入时内联或存到 `assets/`。
- **画板是固定尺寸。** 根元素就是 `w`×`h`，没有响应式视口，媒体查询只会按一个宽度生效。
- **已有可复用的现成能力**：创建项目（`POST /api/projects`）、上传资源（`POST /api/projects/:p/assets`，按内容哈希存）、交给 Claude Code（`apps/server/src/delegate.ts`，每种类型都有 skill）、journal 和冲突重放。导入不需要新的存储或协作机制。

## 2. HTML 素材差在哪

### 2.1 外部 HTML 的常见形态

| 形态 | 例子 | 难点 |
|---|---|---|
| 静态页面，样式在 `<style>` 或外链 CSS | 落地页、邮件模板、导出的报告、AI 生成的单文件页面 | class 样式、外链资源、媒体查询、伪元素、悬停态 |
| 框架构建的 SPA | React/Vue 打包产物 | 源 HTML 几乎是空的，内容靠 JS 渲染出来；只能先跑起来再取 DOM |
| HTML 幻灯片 | reveal.js、Slidev/Marp 导出、impress.js | 一页一个 `<section>`，天然对应幻灯片，但 CSS 远超子集 |
| 设计工具导出 | Figma/Webflow/Framer 导出的 HTML | 大量绝对定位或深层嵌套 div、生成的 class 名 |
| 压缩过的 HTML | 一整行 | 回写是按行显示 diff 的，不格式化会每次都"改了一整行" |

### 2.2 和"可双向编辑"之间的差距

| 差距 | 不处理会怎样 | 处理方式 |
|---|---|---|
| 样式在 class / 外链 CSS 里 | 能显示（`<helmet><style>` 生效），但面板看到的是占位值，改动叠成内联覆盖，源码越改越乱；外链 CSS 直接丢 | 计算样式内联化（§3 B）或 AI 重写（§3 C） |
| 内容靠 JS 渲染 | 画布一片空白 | 先在浏览器里执行，取渲染后的 DOM 快照 |
| 交互（脚本、事件） | 全部失效 | 静态快照为默认；简单的开关/切换可让 AI 改写成 `DCLogic` 状态 |
| `{{` 出现在正文 | 被吃掉 | 转义成 `{{ '{{' }}` |
| 长页面 | 一个 1280×6000 的画板，选中和浏览都不便 | 按顶层区块（`header`/`section`/`footer`）切成多个画板，摆在 `canvas.json` 里 |
| 媒体查询、`:hover`、伪元素 `::before/::after` | 计算样式只取到一种状态；伪元素没有对应的 DOM 节点，无法内联 | 选定一个视口宽度；伪元素转成真实 `<span>` 或保留在 `<helmet>` 里并在报告中列出 |
| 图片、字体是相对路径或外链 | 沙箱加载不了相对路径；自托管字体被 CSP 拦 | 上传进 `assets/`，改写引用；字体能匹配 Google Fonts 的走 Google Fonts |
| 一行压缩的源码 | diff 不可读 | 导入时统一格式化（每个块级元素一行） |

### 2.3 实测：原样包装能走多远

我写了一个典型的静态页面（外链 Bootstrap、`<style>` 里的 class、`onclick`、外链与内联脚本、正文里有 `{{name}}`、表单、图片），只做最朴素的包装：`<head>` 里的 `<style>` 挪进 `<helmet>`，`<body>` 放进一个 1280px 宽的根 `div`，丢掉脚本。然后用 `packages/core` 解析并跑人工操作（临时测试，没有提交）：

- `parseDc` 无报错，26 个元素，其中只有 1 个有内联样式、7 个靠 class。
- 给 `<h1>` 改颜色：回写只改了一行，结果是 `<h1 style="color: #ffcc00">`，与 class 样式并存。
- 改一段文字：正常。
- 但 `{{name}}` 会被当成插值，`onclick` 被丢弃，外链 CSS 不会加载，整个 `<body>` 内容如果原本写在一行里，任何改动的 diff 都是一整行。

结论：**解析和最小回写这一层不需要改动就能接住任意 HTML**；导入要做的是"预处理成编辑器喜欢的形状"，而不是改编辑器。

## 3. HTML 导入的三条路

### A. 原样包装

上面实测的做法，加上 `{{` 转义、格式化、资源本地化。

- 保真度：高（只要页面不依赖 JS 和外链 CSS）。
- 可编辑性：低。能改字、改色，但面板显示的不是源码真实的值，布局改不动（尺寸、间距在 class 里）。
- 工作量：2～3 天。
- 适合：只想"放到画布上看、偶尔改几个字"的素材，或作为 B 失败时的兜底。

### B. 渲染后内联计算样式（确定性转换）

在一个隔离的浏览器环境里真实渲染页面，遍历 DOM，用 `getComputedStyle` 取每个元素的样式，**只保留和"默认值 + 父元素继承值"不同的那部分**写成内联 `style`，去掉 class 和脚本，生成 `.dc.html`。

- 保真度：静态页面很高；SPA 也能处理（先执行再快照）。悬停、动画、媒体查询的其他断点会丢。
- 可编辑性：中高。所有值都在内联样式里，面板显示的就是源码；但布局是"原样冻结"的，可能是浮动、绝对定位或很深的嵌套，不一定是 flex + gap。
- 风险：样式膨胀。不做"减去默认值和继承值"的话，每个元素会带上百个声明。这一步是 B 的核心技术点，需要一套属性白名单（类似 `SLIDE_PROPS`）和默认值表。
- 在哪里渲染，有两种选择：

  | | 在编辑器里（沙箱 iframe） | 在服务端（无头 Chromium / Playwright） |
  |---|---|---|
  | 依赖 | 无新依赖，浏览器就是渲染器 | 需要 Chromium；`pnpm bundle` 现在不带浏览器，嵌进 Tingly Box 后也不会有 |
  | 能力 | 上传的文件；脚本可以在不同源、禁网络的 iframe 里跑 | 还能抓 URL、跑需要网络的 SPA、出截图做比对 |
  | 安全 | 和现有画板沙箱同一套隔离 | 服务端跑不可信页面，要额外限制 |

  建议第一阶段**在编辑器里做**（上传文件 → 沙箱 iframe 渲染 → 抽取 → 交给服务端写文件），URL 导入和 SPA 放到后面，再评估要不要服务端浏览器。

- 工作量：1～1.5 周（抽取与样式精简、资源本地化、按区块切画板、格式化、导入报告、单元测试和一个 e2e）。

### C. 让 AI 按规范重写

把原始 HTML（或 B 的结果）交给 Claude Code，让它按 `.claude/skills/dc-canvas/SKILL.md` 重写成地道的画布文件：flex/grid + gap、字面量文案、有意义的层级、少量 Tweaks。

- 保真度：会漂移。颜色、间距、字号可能被"顺手改好"，长页面可能漏内容。
- 可编辑性：最高，产物和手写的示例项目一样。
- 代价：慢（分钟级）、有费用、结果不可完全复现；需要 `claude` 命令（"交给 Claude Code"现在就依赖它）。
- 工作量：管线本身不大（`delegate.ts` 已有，只需一个导入专用的系统提示和"按画板分批"），2～3 天；难的是验证。

### 推荐：B 打底，C 可选，截图比对贯穿

```
 上传 .html / .zip ──► 沙箱 iframe 渲染 ──► 抽取：DOM + 精简后的计算样式 + 资源
                                                   │
                                                   ▼
                       生成 canvas.json + 每个区块一个 .dc.html（格式化、{{ 转义）
                                                   │
                                   导入报告：截图差异、丢掉的脚本/悬停/断点
                                                   │
                          （可选）按画板「用 AI 整理」──► Claude Code 按 dc-canvas 重写
                                                   │
                                     再比对一次截图，人看差异后接受或撤销
```

理由：

- B 让导入**马上可用且可预期**，不依赖模型和 API key（和现在"不填 key 也能用"的原则一致）。
- C 只在用户想要"更好改"的时候才付出代价，而且是对已经内联化的文件做整理，比直接啃原始 HTML 稳得多。
- 截图比对是"诊断走真实路径"：保真度不靠我们自称，而是每次导入都给出差异图和数字。
- 整理是普通的文件修改，进 journal，可以撤销；"整理"不覆盖原导入，只是一个新版本。

### 目标类型怎么选

- **默认导入为画布**：画布接受任意 HTML/CSS，损失最小。
- **识别为幻灯片的**（reveal.js 之类，或每屏一个 `<section>` 且比例接近 16:9）提供"导入为幻灯片"：每页先走 B 得到内联样式，再用 `checkSlide` 的报错驱动 C 把它压进子集（这一步离不开 AI，确定性转换很难把任意 CSS 映射到子集）。
- 以文字为主的页面（文章、文档站）也可以"导入为文档"：HTML → Markdown（turndown 一类的库），再走 §5。

### 反方向（generate 的另一半）

"parse and generate"里的 generate 有两层：一是生成我们的格式（上面讲的），二是把编辑结果再导出成独立的 HTML 交回原来的地方。幻灯片已有 HTML/PDF 导出；画布目前只有 PNG。补一个"画板导出为静态 HTML"（渲染后的 DOM + 内联样式，去掉 `data-dc-tid`）工作量很小（1～2 天），导入导出就闭环了，建议放进第一阶段。

## 4. AI 能帮在哪里

按"确定性能做的不交给模型"排序：

| 环节 | 谁做 | 说明 |
|---|---|---|
| 渲染、抽样式、本地化资源、格式化、转义 | 代码 | 必须确定、可重复 |
| 切画板 | 代码为主 | 按顶层语义标签和高度切；切不好时可让模型给建议 |
| 结构整理（嵌套 div → flex + gap，绝对定位 → 流式布局） | AI（Claude Code） | §3 C；按画板分批，避免长页面漏内容 |
| 图层命名、去掉无意义的包装层 | AI（快速 AI 或 Claude Code） | 快速 AI 已能在一个画板上逐条执行 jQuery 语句，适合小修 |
| 抽取设计 token | AI + 代码 | 从计算样式里统计颜色、字号、间距的频次（代码），再由模型命名、归并成 `tokens.json`（AI），生成一个设计系统并装进这个画布。这是原版 Design System "从上传的品牌文件生成"的同一种做法 |
| 交互还原 | AI | 简单的标签页、开关、手风琴改写成 `DCLogic` 状态；复杂交互不做 |
| HTML → 幻灯片子集 | AI + 检查器 | 以 `checkSlide` 的 error/warning 作为反馈循环 |
| PPT 的图表、SmartArt | AI（可选） | 先降级为图片；需要可编辑时再让模型重画成形状/表格 |

## 5. Markdown → 文档

文档本来就是 Markdown 文件，这是最便宜的一项。

- 一个 `.md` 文件 → 一个文档项目；默认一个标签页。可选"按一级标题拆成多个标签页"。
- 需要处理的：
  - YAML front matter：取 `title`，其余丢弃或放进第一段说明；
  - 相对图片：一起上传（`.zip` 或多选文件），改写为 `../assets/<file>`；
  - 编辑器不支持的写法：原始 HTML、脚注、数学公式、Mermaid、`<details>`。原样保留（文件里还在，Claude Code 和 git 都能看到），在导入报告里列出"这些块在编辑器里只读或显示为原文"。
  - 第一行补上 `# 标题`（文档约定每个标签页以自己的标题开头）。
- 回写已经是"按块保持原文"，所以导入后用户的原始写法会一直保留。
- 工作量：1～2 天。
- 延伸：Marp/Slidev 风格的 Markdown（`---` 分页）可以"导入为幻灯片"，走 AI 生成，归到第三阶段。

## 6. PPT → 幻灯片

### 6.1 映射关系

PPTX 是一个 zip，每页一份 DrawingML XML，所有元素是绝对定位（单位 EMU），再叠上母版、版式、主题三层继承。16:9 的页面宽 12192000 EMU，正好对应 1920px，即 **6350 EMU = 1px**，坐标换算是精确的。

| PPT | 幻灯片子集 | 难度 |
|---|---|---|
| 文本框、占位符（标题、正文） | 固定定位的 `h1/h2/p/ul`，带 `width` | 中：段落、项目符号、行距、自动缩放；字号下限 24px 和 PPT 常见的 12～18pt 冲突，需要按比例换算后再提示 |
| 图片 | `img` + `assets/` | 低；裁剪（`srcRect`）要换算成 `object-fit`/包一层 |
| 基本形状 | `x-shape`（9 种） | 中：PPT 有约 180 种预设几何，映射不上的转成 SVG（子集允许 ≤ 52KB 的 `svg`） |
| 连接线 | `x-connector` | 中 |
| 表格 | `table` | 中：合并单元格编辑器目前不能改 |
| 演讲者备注 | `<aside>` | 低 |
| 主题色、母版、版式 | 解析继承后写成具体值；可选生成设计系统 | 中高：继承链是 PPTX 解析里最费事的部分 |
| 字体 | `deck.json` 的 `faces`（最多 4 个） | 中：本地字体要找 Google Fonts 替代或上传字体文件 |
| 图表、SmartArt | 先降级为图片 | 高（要可编辑就得 AI 重画） |
| 动画 | `data-build-in` 的有限几种 | 中，只映射能对应上的 |
| 切换 | `data-transition` | 低 |

### 6.2 取舍

- 结果默认是"**全部固定定位**"的幻灯片：每个元素都能选中、改字、改色、拖动，但不是流式布局。这和原 PPT 的心智一致，可以接受；需要时再让 AI 整理成 flex 布局。
- 解析放在哪：JS 生态里没有成熟、完整的 PPTX 读取库（PptxGenJS 只能写），需要用 JSZip + 自己解析 DrawingML；或在服务端用 python-pptx / LibreOffice，但会给 `pnpm bundle` 和 Tingly Box 的分发加一个重依赖。建议自己写一个只覆盖上表"低/中"项的解析器，其余降级为整页或局部图片，并在报告里列出。
- 工作量：可用的第一版 2～3 周，之后长尾很长（母版继承、文字自动缩放、各种预设几何）。
- Keynote、Google Slides 都能导出 PPTX，做了 PPTX 就一并覆盖。

## 7. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户对"导入"的预期是像素级一致 | 导入后觉得"变样了" | 每次导入出截图比对和差异清单；明确说明丢了什么（脚本、悬停、其他断点） |
| 样式膨胀 | 文件难读、diff 大、AI 上下文变贵 | B 的"减去默认值和继承值" + 属性白名单；可选 AI 整理 |
| 不可信 HTML | XSS、外联请求 | 渲染只在不同源、禁网络的沙箱 iframe 里；写进文件前去掉脚本和 `on*` 属性；资源只从上传的文件里取 |
| 大页面性能 | 画板元素上千时选择、回写、快速 AI 上下文都会变慢 | 按区块切画板；导入报告里给出元素数；幻灯片本来就有 200 个元素上限 |
| 只在浏览器里渲染，抓不到 URL 和需要网络的 SPA | 部分素材导不进来 | 第一阶段只承诺"上传文件"；URL 导入作为第二阶段的独立决定（是否引入服务端浏览器） |
| AI 整理改坏内容 | 漏段落、改数字 | 整理只是一个新版本，可撤销；整理前后截图比对；提示词里禁止改文案和数字 |
| 在 Tingly Box 里运行时没有 `claude` 命令 | C 不可用 | B 和 Markdown 导入不依赖模型；C 在不可用时按钮置灰并说明原因 |
| 维护面变大 | 每加一种来源都是一块长尾 | 按阶段做，每阶段用真实素材验收后再决定下一步 |

## 8. 分阶段计划

| 阶段 | 内容 | 估计工作量 | 验收 |
|---|---|---|---|
| **1. HTML 单页 → 画布，Markdown → 文档** | 启动页加"导入"（拖入 `.html`/`.zip`/`.md`）；沙箱里渲染并内联精简样式（B）；资源上传到 `assets/`；按区块切画板；`{{` 转义与格式化；导入报告（截图差异、丢失项）；Markdown 导入为文档；画板导出为静态 HTML；`core` 的单元测试和一个 e2e | 约 1.5～2 周 | 拿 5～10 个真实页面（落地页、AI 生成的单文件页、导出的报告）导入：截图差异小、改字改色改间距都落在内联样式上、回写 diff 只有一行 |
| **2. AI 整理与 token 抽取** | 画板上的"用 AI 整理"（Claude Code，按画板分批，整理前后比对）；从样式里抽取 token 生成设计系统并装入；HTML 幻灯片（reveal.js 等）导入为幻灯片（B + 子集检查驱动的 AI） | 约 1～1.5 周 | 整理后的文件符合 `dc-canvas` 规范（flex/grid + gap、字面量文案），截图差异在可接受范围 |
| **3. PPT → 幻灯片** | PPTX 解析（文本、图片、基本形状、表格、备注、主题继承、字体），其余降级为图片；可选 AI 把固定定位整理成流式布局 | 约 2～3 周起 | 用 5 套真实 PPT 验收：文字可改、版式一致、降级项都在报告里 |
| 待定 | URL 导入、需要网络的 SPA（是否引入服务端浏览器）；Word/Google Docs → 文档 | 单独评估 | — |

第一阶段之后再决定要不要继续：如果用户的素材大多是 AI 生成的单文件 HTML，B 就够用，第二阶段可以缩小；如果大多是 PPT，第三阶段要提前。

## 9. 需要拍板的问题

1. 第一阶段是否只承诺"上传文件"、不做 URL 导入（决定了要不要服务端浏览器）？建议是。
2. 导入后"整理"默认开还是关？建议关：先给确定性结果，用户主动选择整理。
3. 用户手里最常见的素材是哪一种？这决定第二、三阶段的先后。

## 10. 已实施：`@dc/import` 与对照实验

HTML 导入做成了独立的包 `packages/import`（`@dc/import`），编辑器只通过 `packPage` → `extractPage` → `toCanvas` 三个函数用它，可以单独维护和测试。用法和边界见 `packages/import/README.md`。

- **两个入口。** 启动页"新建"里的"导入 HTML"（或直接把文件/文件夹拖到启动页）：在不运行脚本的隐藏 iframe 里排版，适合静态页面。终端 `pnpm dc-import html <文件或 URL>`：在无头 Chromium 里跑完脚本再读，SPA 和需要网络的页面走这里；`--check` 把每个画板经真实沙箱渲染后和原页面做像素比对。
- **怎么读样式。** 不是照抄计算样式，而是只保留作者声明过的属性（按层叠顺序排名，`var()` 解析成值，去掉和浏览器默认相同的），简写保持简写；`::before/::after` 变成真实的 `<span>`；`*` 规则放进 helmet。这是文件能读、能改的关键：计算样式全量内联会让每个元素多出几百个属性。
- **报告。** 丢掉的东西（脚本、悬停态、其他宽度的媒体查询、隐藏元素、透明的滚动动画内容、缺失文件、外链资源）逐项计数，写在画布旁的便签里。

### 对照实验（5 个真实页面，1280 宽，像素差异越小越好）

| 页面 | 确定性导入 | 确定性 + AI 整理 | 只用 AI 重写 |
|---|---|---|---|
| Tingly Box 首页（Vite 构建，886 个元素） | **0.28%**，6 秒 | — | 4.08%，10 分钟，17 万 token |
| Tailwind 落地页 | **0.01%**，8 秒 | 0.01%，文件小 19% | 0.09%，3 分钟 |
| HTML 邮件（表格布局） | **0.00%** | — | 0.00%，30 秒 |
| vCard 个人主页 | **0.00%** | — | 3.35%，2.5 分钟 |
| Start Bootstrap 落地页 | **0.00%**（切成多个画板时 0.62%） | 0.00%，文件小 20% | 8.14%，76 秒 |

- **只用 AI** 在简单页面上可以很好（邮件、Tailwind 落地页），但它看不到渲染结果，高度和间距靠推算，误差会逐段累积（Bootstrap 页 8%，越往下偏得越多）；长页面又慢又贵，还会"补全"原页面当时并没显示的状态。
- **确定性 + AI 整理** 保住了像素（0.00～0.01%），AI 只做它擅长的：把重复样式提成类、删冗余声明，文件小约 20%。这条路线成立：AI 的输入是已经对的结构，出错面小，而且可以用 `--check` 验证。
- **确定性导入的已知短板**：滚动时才出现的内容会以透明状态导入（首页 24 处，报告里会提示）；终端导入会先慢速滚动一遍并结束 CSS 过渡来减少这种情况，编辑器里不运行脚本则无法补救。
- 实验输入、输出和截图不在仓库里；复现方法是对同一批页面运行 `dc-import html <url> --check --split off`。

## 11. SVG → 画布，以及模块的分层

模块按"来源 → 页面模型 → 生成器"分三层：`src/sources/<来源>` 只负责把一种素材读成 `model.ts` 里的页面模型；生成画板、导入报告、资源搬运、像素比对都是共用的。加一种来源（Figma、HTML 幻灯片）就是在 `sources/` 下加一个目录，不碰其他来源。

SVG 是第二个来源（`sources/svg/read.ts`）：
- **不排版、不拍平**：SVG 本身就是带坐标的图形树，原样作为内联 SVG 放进一个画板，尺寸取自它的 width/height 或 viewBox。文字保持为 `<text>`，颜色和描边保持为属性；属性面板对 SVG 形状改的就是 `fill`、`stroke`、`stroke-width`、`opacity` 这几个属性，回写只动一处。
- **去掉画布接不住的**：脚本、`<foreignObject>`、Inkscape/Illustrator 的私有命名空间和 metadata，计数写进报告。
- **嵌入的位图搬出来**：Figma 导出的 SVG 会把截图以 base64 嵌在里面，超过 2 KB 的 `data:` 文件都存成 `assets/` 下的文件（HTML 也一样）。原文件本身放 `uploads/`，见 §12。
- **入口**：编辑器里"导入 HTML 或 SVG"可以选文件、拖文件，或者直接 ⌘V 粘贴从 Figma "复制为 SVG"得到的代码；终端是 `dc-import svg`。

用 YZ 给的一份 Figma 复制的 SVG（830×400，2.1 MB）实测：
- 像素差异 0.00%，画板文件 45 KB，两张截图搬进 `assets/`。
- **Figma 复制或导出的 SVG 默认把文字转成了路径**，所以导入后能改颜色和位置，但改不了字。报告会提示：导出时取消勾选 "Outline text" 就能保留文字。要拿到 Frame、自动布局、文字样式这些真正的结构，还是要走 Figma 的 API（§0 之后讨论的 Figma 导入）。

## 12. 导入的原文件放哪：统一进 `uploads/`

和对话附件（[attachments.md](./attachments.md)）用同一个目录、同一条规则：**人带进项目的东西都放 `uploads/`，用的地方直接引用，不再复制一份。**

| 带进来的是 | 放在 | 说明 |
| --- | --- | --- |
| 单个文件（一个 .svg、一个 .html、粘贴的 SVG） | `uploads/<名字>-<内容哈希8位>.<扩展名>` | 和对话附件的命名一样，同样的内容只存一份 |
| 一个文件夹（网页连同 css、图片、字体） | `uploads/<文件夹名>-<哈希8位>/…` | 保留原来的目录结构，相对路径不变；页面目录以外的文件（字体 CDN、外链图片）放 `_ext/<域名>/…` |
| 从文件里抠出来的（SVG/HTML 里内嵌的 base64 图片） | `assets/embedded-<哈希>.<扩展名>` | 原文件里没有单独的这份文件，是导入时派生出来的 |

- 画板里的图片、字体直接指向 `uploads/…` 下的原文件；`canvas.json` 的 `imported.original` 记着入口文件，以后要重新导入或对照原样都从这里取。
- 服务器端：`isKeptPath`（`packages/core/src/attachments.ts`）定义 `uploads/` 下允许的路径（最多 12 层，扩展名是可附加的类型或字体）；`PUT /api/projects/:p/uploads?path=` 按路径写入，单个文件经 `POST …/assets?dir=uploads` 按内容命名。
- 编辑器和 `dc-import` 结果一致：五个对照页面重新导入后像素差异不变（0.00%～0.30%），图片和字体都从 `uploads/` 加载。
- 导入失败会留下一个空项目，还没有删除项目的接口，后面补。
