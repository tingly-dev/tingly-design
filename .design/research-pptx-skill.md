# 调研：从 Anthropic 的 pptx 技能学什么，来提升 slides 的生成效果

状态：**研究**。结论已拆成 #500（生成准则，随本笔记一起实施）、#501（deck 级检查）、#502（编辑器内自检回路）；PPTX 导出的可编辑性交给另一项工作，这里只留证据。

对象：[anthropics/skills `skills/pptx`](https://github.com/anthropics/skills/tree/main/skills/pptx)。读的是现行版 `e4bb5d9`（2026-11-16）的 `SKILL.md` 与 `scripts/`，以及它的三代前身：`ef74077`（2025-12，html2pptx 时代，含 `html2pptx.md`）、`4e6907a`（2026-02，pptxgenjs + “Design Ideas” + 强制 QA）、`fa0fa64`/`1780c5e`（2026-07/11，加入“结构化 deck”和内容结构）。我们这边对照 `.claude/skills/slides/`（SKILL.md 与 `reference/` 七页）、`apps/server/src/delegate.ts` 的 `SLIDES_SYSTEM`、[slides-variety.md](./slides-variety.md)、[drawn-check.md](./drawn-check.md) 和 `check --snapshots` 的版面探针。

## 1. 结论

它做出来的幻灯片好看，主要不是因为 python-pptx / pptxgenjs（那是它的底层，我们不搬），而是四件写在技能里的事：

1. **动笔前把“样子”定死，而且定得具体**：按题目选配色，一个颜色占主导、一两个辅助、一个锐利的强调色少用；用“换到别的 deck 也成立就不够具体”来检验；选一个贯穿全篇的视觉母题。
2. **每页都要有可看的东西**：明说“纯文字页会被忘记”，给出版式和数据呈现的具体选项（双栏、图标行、2×2 网格、半出血图、60–72pt 大数字、对比栏、时间线）。
3. **一张短而可检查的禁用清单**：标题下的强调线、贯穿的色带、边缘色条和单边色框、标题句号、正文居中、默认米色底、间距随意、只精修一页。这张单子是迭代出来的：2025 年版还**推荐**“标题下 3–5pt 下划线”“单边粗边框”，现行版把它们列为“AI 生成的标志”。
4. **必做的看图自查**：先查内容（残留占位文字用 grep 找），再把每页渲染成图，用“新眼光”（子代理）按一张具体清单看（溢出优先、重叠、间距不均、对比、断词与数字单位拆行、同类页之间比标题位置），改完只重看改过的页，然后停。

我们的 slides 技能在**机制**上比它细（封闭子集、高度预算、版式惯用法、字体、图表与图解配方），但在这四件事上要么没有，要么写在新 deck 不读的页里。#500 把可直接吸收的部分写进了技能；同题前后对比（§5）显示母题、版式变化和禁用项立刻见效，而“内容只占上半页、字偏小”这类问题光靠文字准则改不掉，需要 #501 的检查和 #502 的回路把它变成 agent 能看到的警告。

## 2. 它为什么好看：逐条拆开

| 做法 | 技能里怎么写 | 为什么有效 |
|---|---|---|
| 先定调 | “Before Starting”：按题目选配色；主导色占 60–70% 视觉重量，1–2 个辅助色，一个锐利强调色；深色封面与结尾、浅色内容页（“三明治”），或全程深色；**选一个母题并在每页重复**（圆角图框、彩色圆里的图标），色条不算母题。旧版还要求“写代码前先说出你的设计思路” | 模型最容易滑向“每页各自好看、合起来没有性格”。主导色 + 母题让整份 deck 一眼是一套东西；题目检验阻止默认蓝 |
| 每页一个视觉元素 | “Every slide needs a visual element — image, chart, icon, or shape. Text-only slides are forgettable.” 给出版式选项与数据呈现选项 | 直接压掉“标题 + 一段话 / 一串要点”这种最常见的草稿页 |
| 硬规则 | 字号表（标题 36–44pt、小节 20–24pt、正文 14–16pt、注释 10–12pt）、0.5" 最小边距、块间 0.3–0.5" 且全篇一致、字号下限（不够放就删字、放大容器或拆页，不缩字） | 给模型可执行的数，而不是“要可读”；注意它默认的 16:9 画布是 10" 宽，按画布宽度折算，这套正文比我们 1920 px 下的 28–32px 大约三成（若用 13.33" 宽则与我们相当；技能没说用哪个，这是推断） |
| 禁用清单 | “Avoid (Common Mistakes)”，见 §1 第 3 条，另有“不要重复同一版式”“标题在同类页上不漂移”“图表标签全篇一致”“低对比的图标” | 每条都是看得见、可判断的；而且是从真实输出里总结的（下划线强调从“推荐”变成“禁止”） |
| 内容结构 | 一页一个信息；金字塔（结论先行、执行摘要、分节、结论与下一步）；按用途定篇幅（现场讲 vs 预读，1.5–2 分钟一页） | 版式之前先把故事理顺，页数和每页字量随之合理 |
| 写法约束（html2pptx.md） | 所有文字必须在 `p`/`h1–h6`/`ul`/`ol` 里；不写手打的“•”；图表区用占位块；转换时**内容溢出就直接报错** | 与我们的封闭子集同一思路；“溢出即失败”对应我们的版面探针 |
| 看图自查 | 2026-02 版：“假设有问题，你的工作是找出来”“即使 2–3 页也用子代理”“至少完成一次修改-复查循环”；现行版收敛为：第一次渲染通常有几处真问题，找出来、只重渲改过的页、然后停。配一张具体清单 | 生成代码的人看不出自己的错；清单让“看”变成可执行的检查。后来的收敛避免了为找问题而过度修改 |
| 模板与全局视图 | `thumbnail.py` 出全 deck 缩略图网格，先看全貌再选版式；`slide_text.py` 把每页文字、表格、图表数据、备注抽成 Markdown | 跨页比较（标题漂移、版式重复）要求一次看到所有页 |

## 3. 我们差在哪，吸收了什么

| 方面 | 我们原来 | 差距 | #500 的处理 |
|---|---|---|---|
| 配色 | “一深一浅、1–2 个强调色、两种底色加一张强调页”，有对比度和色弱要求 | 没有“谁主导”，没有题目检验，没有禁止默认蓝和米色 | 加主导色/辅助/少用强调色、题目检验、不默认蓝、不默认米色底 |
| 母题 | 无 | 缺 | 新增“一个母题贯穿”，举例并排除色条 |
| 每页有可看的东西 | “一页一个想法；把列表变成表格、卡片、大数字或引语”；`images.md` 说“图标少用”“没有图片也是合格的 deck”；共用规则“偏向极简” | 允许标题 + 段落的纯文字内容页 | 每个内容页要有正文以外可看的东西，且**取自内容**（数字、表格、柱、图解、图片、并列项的图标、放大的引语），没有就把那句话本身放大；仍禁止为凑视觉而加填充；`images.md` 写明图标何时值得用 |
| 字号 | 下限 24px；`craft.md` 正文 28–32px | 放映场景偏小，对比实验里正是“字小、页空” | 现场放映：句子 36–40px、标签注释 ≥28px（页脚 24px 不变）、标题 80–112px、大数字 ≥160px；阅读型 deck 可 28–32px；“页面显得空先放大或铺开，再考虑加东西” |
| 禁用清单 | 一部分在 `craft.md` 末尾（新 deck 必读的是 layout/styles/fonts，不含它）；`styles.md` 反而教“用 `border-left` 给引语画强调竖条” | 新 deck 读不到；自相矛盾 | “Never” 一条进 SKILL.md；删掉 `styles.md` 的竖条用法 |
| 篇幅 | 问长度与听众 | 没有按用途定字量 | 第 2 步加“现场讲约 1.5–2 分钟一页、字少；预读自带完整叙述” |
| 自查 | “Look at what you made” 只讲命令与警告含义 | 没有怎么看、看什么、何时停 | 加看图流程（陌生人视角/子代理、改、只重看改过的、停）和具体清单（溢出优先、重叠与页脚相撞、间距、对比、断词与数字单位拆行、同类页之间比较、内容只占上半页、残留占位） |
| 示例变成默认 | 示例与参考页里的颜色、字号是具体值 | 模型会把示例当风格 | 明写“示例只示范语法，不是本仓库的风格” |

没有吸收的：它的 10 色配色表（会把所有 deck 拉向同几套颜色）、pt 字号表原样（我们用 px 并按 deck 尺寸写）、0.5" 边距（我们 128px 更宽）、“假设一定有错、至少改一轮”的旧措辞（现行版已放弃，我们取“找真问题、改、停”）。

## 4. 不让每份 deck 长得一样

吸收准则最大的风险是所有 deck 收敛成同一个“好看模板”。做法：

- 只写**原则和检验**，不写具体配色、字体、版式套餐；母题给的是一类手法的例子，要求“为这份 deck 选”。
- 题目检验（“换到别的 deck 也成立就重选”）本身就是反同质化的。
- 明写示例只是语法；原有的“相邻页不同版式、同一模板不连排三页、分节处换底色”保留。
- 设计系统与 36 个内置 look 仍优先于这些默认判断。
- 对比实验里两份 deck 选了完全不同的母题（等宽编号眉题 vs 右上角超大衬线序号）和不同的配色，见 §5。

## 5. 前后对比

**方法**：同两个薄 brief（8 页面包连锁季度汇报 “Crumb & Co”；6 页开源笔记应用 meetup 讲稿 “Driftwood”），各生成一次：“前”用 main 上的技能副本，“后”用 #500 改过的副本；每次一个干净的子 agent（同一模型 sonnet），只读给它的技能，用同一条 `tingly-design check --snapshots` 看图自查后停。图由同一 CLI 画出，拼成联系表（project library `outputs/evaluate-pptx-skill-for-our-proj/{before,after}-{qbr,driftwood}.png`）。

| 观察 | 前 | 后 |
|---|---|---|
| 母题 | 两份都没有 | 都有：Driftwood 每页等宽 “0N / …” 眉题与页脚；Crumb 内容页右上角超大衬线序号 01–05 |
| 版式变化（Crumb） | 封面、KPI 卡、柱+大数字、两卡、对比、三卡、强调页、致谢：卡片页占一半 | 封面、大数字+柱、两卡、时间线、表格、强调页、三卡、决定页：多了时间线与表格 |
| 禁用项 | 封面左上一条短强调线；引语左侧强调竖条 | 都没有 |
| 字号（源文件里的 `font-size` 计数） | Driftwood 标题 72px，正文多为 24–28px；Crumb 用了 22 处 24px | Driftwood 标题 88px，出现 10 处 36px 正文；Crumb 的 24px 降到 8 处 |
| 内容只占上半页 | Crumb 3 页、Driftwood 2 页明显 | 仍有（Crumb 的两卡、时间线、表格页；Driftwood 的卡片页），agent 看到了但判断“可接受” |
| 米色底 | Crumb 用奶油底 | 仍是暖浅色（与面包题目相关，可算“为题目选”，但接近米色） |
| 自查轮数 | 3 / 3 轮 | 3 / 2 轮 |

加上 deck 级检查之后（`check --snapshots` 多报占位、过小的字、拆行、只占上半页、标题漂移），用同一个 Crumb brief 再跑一次（project library `outputs/evaluate-pptx-skill-for-our-proj/checked-qbr.png`）：第一轮检查报了两页内容只到 55%、60% 的高度和一处低对比，第三轮报了一个被拆成两行的 “€4.1M”；agent 把卡片页拉满了高度、加深了数字颜色、放宽了卡片，第四轮干净。和只改准则的那次相比，“只占上半页”这一项被检查点名后真的改了。仍是单次样本。

**读法与边界**：每个 brief 只各跑一次，模型有随机性；评判是我看图的判断，没有用评审模型。能下的结论只有：母题、版式变化、禁用项这类**能写成明确指令的**改进立刻被采用；“页面用满、字够大”这类**需要看图判断程度的**，agent 看到了也倾向于放过——这正是 #501（把“内容只占上半页”“字低于下限”变成警告）和 #502（编辑器里的 agent 也能拿到这些警告和图）要补的。为了以后能重复量，加了评测题 `evals/tasks/crumb-review.json`（评分表按本节的准则写），可用 `pnpm eval -- --task crumb-review --route skill --runs 3 --judge` 做多样本对比（要花钱，本次未跑）。

## 6. 导出、自检与模板

**PPTX 导出**（另一项工作负责，这里只留证据）：用真实 CLI 导出一个两页小 deck，再用 python-pptx 读回：三行 `h1` 成了 3 个文本框，一段含 `<b>` 的话成了 5 个，列表每个“•”单独一个文本框；没有标题占位符、没有 `txBox="1"`、主题是 pptxgenjs 默认 Office 主题、`deck.json` 的 `sections` 没有成为分节。原因在 `packages/export/src/pptxDom.ts` 的 `text()`：逐行、逐 run 输出 `wrap="none"` 的文本对象。技能的“结构化 deck”（一个文本块一个文本框、原生项目符号、标题占位符、主题色与字体、分节）是对照。样例 deck 与成品在 project library 的 `outputs/evaluate-pptx-skill-for-our-proj/`。

**编辑器内自检**：编辑器里委托的 Claude Code 只有 `Read,Edit,Write,Glob,Grep`（另加图片生成），`SLIDES_SYSTEM` 写着 “Do not run builds, servers or browsers”，没有任何版面结果回传；看板已有 `.runs.json` 的 `drawn` 回路。→ #502。

**deck 级检查**：`check --snapshots` 逐页看裁切、出界、对比、挤压、空白；缺跨页比较（标题漂移）、残留占位、字号下限（`checkSlide` 只记 `note`，不进 `check`）、断词与数字单位拆行、内容只占上半页。→ #501。

**模板与读取**：技能的 `slide_text.py` / `thumbnail.py` 对应我们可做的两件小事：PPTX 作为请求附件时给模型一份按页文字提要（导入器已能解析，PPTX 目前不是可解析附件）；`look` / `check --snapshots` 出一张全 deck 联系表，便于跨页比较。未开 issue，等需要时再提。

## 7. 不适用的部分

- **让 agent 直接写 pptxgenjs 或改 OOXML**：我们的 deck 是编辑器双向编辑的文件，PPTX 只是交换格式；[slides-pptx.md](./slides-pptx.md) 已定不回写原 OOXML、不维护第二份编辑状态。
- **LibreOffice 渲染做 QA**：我们的真相是编辑器自己的渲染，产品不依赖 Office/LibreOffice/Python；它关于“QA 渲染器换字体导致溢出判断失真”的提醒只在 PowerPoint 端字体不同时成立，属于导出工作。
- **pptxgenjs 的坑**：对我们是 writer 内部问题，agent 碰不到。
