# 跨类型嵌入：把另一个项目的一页，当作一个元素放进当前作品

状态：**方案**（等人定 §10 的几件事；还没有实现，没有改任何格式）。先例是 [import-from-project.md](./import-from-project.md)（画布画板 → 幻灯片、动效，已实施），这份把它推广到六种类型，并回答它当时留下的"来源变了怎么办"。对应 issue 是 #53。

稿子画在自身设计稿里：`projects/tingly-design-ui-canvas` 的 `LinkedInsert`（入口和选择器）、`LinkedItem`（元素、面板、状态、支持表）两块板（[self-design.md](./self-design.md)）。

## 1. 要解决的问题

人说的是："文档把画布的一页当图用；幻灯片把看板当一个元素放进来；诸如此类"，也就是**在一个作品里放另一个作品的一页**，并且它是**链过来的**，不是死图：原作品改了，这里能知道、能一键跟上。

今天能做到的只有一种：画布的画板，放进幻灯片和动效（`<x-embed src="uploads/…">`，`imports` 记来源，手动"从原画板更新"）。其余都做不到：

- 文档只有 Markdown 图片，要把画布的一页放进来，只能先导出 PNG、再拖进去，之后画布改了没人知道；
- 幻灯片、动效放不进看板、文档、幻灯片的页；
- 画布、看板、设计系统不接收任何项目的页面；
- 已有的画板导入没有"原画板变了"的提示（import-from-project.md §5 明说推迟了）。

结论：**"记下来源"已经解决，"运行时依赖来源"才是要不要碰的事**。而人的话里要的是前者加一句"变了我知道、能跟上"。

## 3. 考虑过的做法

| 做法 | 好处 | 问题 |
|---|---|---|
| A. 复制 + 来源，一对一对推广（现状的延长） | 自足；每一对独立交付 | 每一对各写一套复制/检查/导出规则；仍然没有"变了"的提示；人看到的是六套互不相干的入口 |
| B. 活引用：`<x-embed src="projects/<句柄>/…">`，渲染时去读 | 没有副本、没有过期 | 推翻已记下的决定；导出/zip 要在导出时内联，之后不再活；源被挪走静默断；源的改动静默改了成品；沙箱、四条导出路线、委托的只读授权都要长出跨项目的手 |
| **C. 链接的副本（采用）**：副本仍是运行时唯一的真相，来源记录升级为"链接"：知道原作品变了、一键更新、可选自动更新；用什么形态显示（图片或活的元素）是另一条轴 | 不动运行时、不动导出、不动 zip；"链"的体验由记录给；各类型一次接上 | 有副本占空间；"活"的元素是冻结了数据的活（§5.3）；要把现有 `imports` 推广 |

选 C：**用户要的"链"是知道和跟上，不是运行时依赖**。副本在，项目就自足；记录在，就能比较、能更新。这也是 #53 上"先让来源可操作、再按需加配对、活引用继续否决"的建议的落地，只是把"一对一对加"换成"一个模型、一张支持表"。

## 4. 模型：链接的页面（linked page）

### 4.1 它不是新元素

**一个链接的页面就是目标作品里一个普通的元素，加上索引里一条记录。** 没有新语法：

| 目标 | 显示成图片 | 显示成活的元素 | 记录放在 |
|---|---|---|---|
| 文档 | `![说明](uploads/linked/<id>/页.png "图片说明")`：一张普通 Markdown 图片 | 不支持（§5.4） | `doc.json` |
| 幻灯片、动效 | `<img src="uploads/linked/<id>/页.png">`（钉住的图片） | `<x-embed src="uploads/linked/<id>/…" data-props>`（已有，推广） | `deck.json`、`motion.json` |
| 画布 | 画板里的 `<img src="uploads/linked/<id>/页.png">` | 不支持（§5.4） | `canvas.json` |
| 看板、设计系统 | 不支持（§4.5） | 不支持 | — |

因此：Claude Code、旧版编辑器、微信/Word/Markdown 导出看到的都是它们本来就懂的东西；`pnpm`/`check` 只需把 `isBoardEmbedPath` 放宽到"`uploads/linked/<id>/` 下记录里的页"。

### 4.2 记录

目标索引文件（`deck.json` / `motion.json` / `canvas.json` / `doc.json`）的 `imports` 数组里（已有，未知键本来就保留；画板导入的旧记录原样有效，缺的字段按旧默认读）：

```json
{
  "path": "uploads/linked/k3f9/Hero.dc.html",
  "from": "projects/brand-site",
  "rel": "sub/hero",
  "kind": "design",
  "page": "Hero.dc.html",
  "mode": "live",
  "sync": "manual",
  "at": "sha1:9c1e…",
  "copiedAt": "2026-11-18T09:12:00Z"
}
```

| 字段 | 含义 |
|---|---|
| `path` | 副本的位置，**也是这条记录的键**（和现在一致）。新链接放在 `uploads/linked/<id>/`（`id` 四到六位随机，创建时定下、之后不变，与任何名字无关），所以来源项目或页面改名、挪动都不动副本；旧的 `uploads/<来源>-<画板>/` 保持有效 |
| `from` | 来源项目的句柄（`projects/<句柄>`，别名解析，同 `designSystems.artifact`） |
| `rel` | 来源在**本项目文件夹里面**时的相对路径（子项目，§8）；解析时先看它，所以复制、fork、zip 后仍然对得上 |
| `kind`、`page` | 来源的类型和页的稳定编号：画板文件名、幻灯片 `slides/<id>.html`、文档标签页 id、场景 id、看板的 `index`（看板只有一页）、设计系统的页 id。**不用标题**，标题是标签 |
| `mode` | `live` 或 `image`（§5） |
| `sync` | `manual`（默认）或 `auto`（§6.4） |
| `at` | 复制时来源那一页（和它依赖的文件）的内容哈希；"原作品变了"就是现在的哈希和它不同。核心的一个纯函数 `pageHash(kind, files, page)`，来源由 `GET /api/projects/:p/files` 读（`BoardPicker` 已经在读） |
| `copiedAt` | 同现在 |

**同一页被放两次**：副本是按"来源页"一份（再导入同一页覆盖同一副本，所有指向它的元素一起变，现状如此）；每个元素自己的东西（位置、大小、`data-props`、适配方式）留在元素上。**图片形态**是副本里的一张 PNG，**活的形态**是页的源文件；同一页同时有两种用法时两份文件共用一条记录（`mode` 是元素的事，记录里存的是"最近一次的"用来初始化；见 §10 第 2 条）。

### 4.3 为什么是稳定编号，而不是路径或名字

[project-identity.md](./project-identity.md) 已经把"名字当键"的坑走过一遍：名字可重复、会改。所以页用文件名/id 记，项目用句柄（路径生成）加 `rel`。**句柄解析不到时不报错**：副本在，元素照常显示，面板里标"找不到原作品"（§7.3）。

### 4.4 复制、复制粘贴、fork

- 复制整个项目（fork）或打 zip：记录和副本一起走，`rel` 的来源在树里就仍然活着，不在树里就成为"原作品不在这里"，元素照常。
- 元素在项目之间复制粘贴：和今天粘贴一张图一样要把 `uploads/` 里被引用的文件带过去；这一条随第 2 期定，不在第 1 期（§9）。
- zip 导入时 `from` 句柄会撞名重命名：`projectArchive.ts` 的 `renameSystems` 只改写 `designSystems`，这一步要推广成改写 `imports[].from`（第 1 期要做的小事，现有画板导入已经有这个洞）。

### 4.5 看板和设计系统作为目标：不接

看板的页面脚本之外没有"放一张图"的位置：图片只许 `data:`、每个文件 ≤ 256 KB（一张 2× 的 PNG 轻易超过），也丢掉 `iframe`。想在看板里放别的作品的页，应该是看板自己的一个"图片块"，那是看板的功能，不在这里。设计系统是 tokens 和组件，页面不是作者写的 HTML，README 虽是 Markdown 但它只管"怎么用这套系统"，不放别的作品的图。两者写进矩阵（§5.1），理由写明。

## 5. 支持哪些：来源 × 去处

### 5.1 矩阵

● 活的元素（运行时在框架里画，缩放铺满）；○ 图片（来源那一页的 PNG，来源变了重画）；✗ 不接，理由在表下。"已有"是今天已实施、本方案只把它并进同一个记录和同一个入口。

| 来源的页 ＼ 放进 | 画布 | 幻灯片 | 文档 | 动效 | 看板 | 设计系统 |
|---|---|---|---|---|---|---|
| 画布的画板 | ○ | ●（已有；`$time` 的画板会动）、○ | ○ | ●（已有，逐帧）、○ | ✗ | ✗ |
| 幻灯片的一页 | ○ | ○ | ○ | ○ | ✗ | ✗ |
| 看板（整页） | ○ | ●（第 2 期，冻结数据）、○ | ○ | ○（见下） | ✗ | ✗ |
| 文档的一个标签页 | ○ | ○ | ○ | ○ | ✗ | ✗ |
| 动效的整段 | ○（GIF） | ○（GIF 或封面帧） | ○（GIF 或封面帧） | ○（GIF） | ✗ | ✗ |
| 设计系统的一页 | ○（按需） | ○（按需） | ○（按需） | ○（按需） | ✗ | ✗ |

每一格为什么：

- **画布 ← 画板（图片）**：画板里是 `<img>`；画布的画板是模板 HTML，不认 `<x-embed>`（只有幻灯片和动效的页认，`template.tsx` 里 `ctx.slide` 分支），所以画布只能收图片。画布 ← 画布想要"活的"，等价于把画板复制成自己的画板，`dc-import` 只认同目录的兄弟文件，是否能指到 `uploads/` 下还没验证，列在 §10。
- **幻灯片 ← 看板（活的）**：看板的框架本来就是一个沙箱 iframe，由编辑器 `postMessage` 喂页面和数据，形状和 `XBoard` 一样，所以能做；数据是**冻结的行**，不是活查询（§5.3）。放映和编辑时都能看，导出 PDF/PPTX/PNG 时落成图片（§6.6）。
- **动效 ← 看板（只给图片）**：动效视频逐帧渲染，元素必须能按时间点 seek；看板的页不是 `time` 的函数，活的版本每次渲染的帧不一样，违反"视频逐帧确定"（[import-from-project.md](./import-from-project.md) §3.4）。所以动效里的看板是它那一刻的图片，面板里直接说明。
- **文档 ←（只给图片）**：文档的出口是 Markdown、HTML、PDF、Word、微信，除 HTML 外都没有"活的元素"，微信更是只收图片；所以文档里的链接页是一张普通 Markdown 图片。这样 Word、微信、Markdown 导出不用写任何新规则（`wechatHtml.ts` 的 `picture` 照原样处理）。
- **动效 → 别处（GIF）**：动效已能导出 GIF，GIF 在幻灯片和文档是图片（放映时会动）、在动效是片段（[gif-images.md](./gif-images.md)），所以"动效的一段放进幻灯片或文档"的第一版就是它的 GIF，要静止的就取封面帧（动效有封面）。幻灯片 ← 动效场景做成活的元素是第 3 期，要先回答场景的时间语义。
- **幻灯片、文档 → 别处（图片）**：幻灯片的页是封闭子集的 HTML、文档是 Markdown，都没有"在别的页里运行"的用法，所以第一版只给图片。文档的标签页通常很长：图片按页宽缩放、高度随页，由人用裁切高度（第 2 期）或只选一段。
- **看板、设计系统作为去处 ✗**：见 §4.5。
- **设计系统 → 别处**：它的页（颜色、字体、组件）是编辑器自己的视图，不是作者写的页面，图片已能从导出菜单得到；价值低，所以"按需"。

### 5.2 图片形态

副本是一张 PNG（默认 2×），放 `uploads/linked/<id>/<页>.png`，页的像素尺寸记在元素上（幻灯片、画布）或不记（文档按 Markdown 图片）。**重画不新写一套**：服务端走 `pageExport` 让本机 Chrome 打开编辑器、打开来源项目、显示那一页、点它自己的"PNG 图片 @2x"菜单项——命令行 `export --as png` 和 `check --snapshots` 已经这样做，所以"人在导出菜单里看到的"和"链接里的图"是同一份，不会各画各的。没有 Chrome 的机器（`GET /api/render` 能查）：画布画板仍可由编辑器在浏览器里画（`BoardPicker` 已能在别的项目里画画板，`nodeToPng` 已有），其余类型提示"这台机器没有 Chrome，不能更新这张图"，图保持原样。**这条是要在第 1 期实现里先做个试验确认**：编辑器内服务端调用 `pageExport` 的 `inServer` 路径是否能给任意句柄的项目出任意一页（代码里有 `inServer` 参数，我没有在这次设计里跑过）。

### 5.3 活的形态

- **画板**（已有）：副本是画板和它挂的兄弟画板、用到的 `uploads/`、`assets/` 文件，`XBoard` 在自己的 iframe 里画，`$time` 让它会动。
- **看板**（第 2 期）：副本是 `files/` 下的页（含样式和脚本）加**每个数据集当时的行**，冻结成文件数据集（看板里"暂停的查询"已经是这个形状：文件数据集带 `request`，见 `dashboard` 技能）。刷新就是在来源项目上重新跑一遍查询、再冻结。所以放进幻灯片的看板是**离线、确定**的：不连数据库、不带来源的 `data/*.db`，也不因来源的连接器而变。代价是它显示的是复制那一刻（或最近一次更新）的数字，面板上写着这一时刻。`DashApp` 是怎样把数据集交给框架的、一个嵌入怎样复用同一段代码，要在第 2 期开头做个试验；这次没有核实。
- 每个活的元素是一个 iframe 里的运行时，数量上受幻灯片"每页至多 8 个嵌入（`MAX_EMBEDS`）"约束；编辑状态下它们停在静止帧、不接指针，放映时才运行（画板的做法，`XBoard` 的 `live`）。

### 5.4 活的元素为什么只有幻灯片和动效

只有这两种类型的页是"一块固定画布上钉着的元素"，嵌入有位置有大小，能缩放铺满；文档是流式文字，画布的画板是模板 HTML。不是做不到，是每多一个去处就要多一条导出规则，而表里的 ○ 已经满足"放进去、能更新"。要给画布活的版本，等 `dc-import` 的问题查清（§10）。

## 6. 渲染、写回与导出

### 6.1 选中与编辑的边界：整块，不钻进去

链接的页面在目标里是**一个整体的元素**：能选、搬、缩放、删、复制，面板里有它的表单；**不能在里面点选、改字、拖元素**。理由是几条硬的：

- 每个项目有自己的写回引擎、撤销栈、锁、日志和一个 Claude Code 会话（`.claude-session.json`）；在 A 里改 B 的页，要决定这一步属于谁的撤销、谁的日志、谁的"正在运行时拒绝改"，这是活引用的另一半麻烦；
- 副本不是源：改副本不会回到源，改源又会被下次更新盖掉，两头都会让人困惑；
- 画板的嵌入今天已经是这样（面板改它的 Tweaks，不钻进画板）。

"我想改这一页"的出口是面板里的**打开原作品**（在原作品里打开那一页，改完回来，副本按 §6.4 更新）；这也是 [ux-principles.md](./ux-principles.md) 第 11 条"把下一步的物件交到手上"。画板的 Tweaks（`data-props`）是例外：它们是来源作者留出来的旋钮，仍由面板改，写在元素上。

### 6.2 来源变了：怎么知道、怎么更新

- **知道**：打开项目时，以及目标页上有链接元素的那一页被打开时，按记录的 `at` 去比（读来源的 `GET /api/projects/:p/files` 然后 `pageHash`，来源不可读就不比，面板里写"没法检查"）。不轮询，不后台跑。
- **更新**：面板里的"更新"，一次点击做三件事：重新复制来源页（图片形态则重画 PNG）、改写 `at` 与 `copiedAt`、让所有指向这份副本的元素一起变；这是**一步撤销**（编辑引擎的 `group`，面板的撤销同一个）。
- **全部更新**：项目菜单里"更新所有链接的页面（N）"，只在有过期的时候出现。
- 没有"来源改了就悄悄变"，即使 `sync: auto` 也只在**打开目标项目的时候**才更新（§6.4），并留一条记录在变更日志里。

### 6.3 性能

- 图片形态只是一张图：和今天的图片一样，没有运行时。重画只在人点"更新"、或 `auto` 打开项目时，一张图几百毫秒到几秒（要起 Chrome），后台做，元素先显示旧图，画好后换（**不阻塞编辑**）。
- 活的形态每个是一个 iframe：编辑状态停在静止帧、不接指针，放映和播放才运行；每页至多 8 个（`MAX_EMBEDS`）。幻灯片的缩略条和启动页卡片不跑活的框架（启动页现在也不画嵌入的画板，import-from-project.md §5，这条与"画嵌入"的修补一起做，见 §9）。
- 副本占空间：图片 100–500 KB，画板几十 KB，看板带冻结行时受数据大小限制（`DASH_DATA_MAX`）。

### 6.4 "保持更新"（`sync`）

只有一条轴、两个值：`manual`（默认）：变了只提示，人点才更新；`auto`：打开目标项目时若来源变了就自己更新。**默认值**按来源在哪里定（[ux-principles.md](./ux-principles.md) 第 6 条，聪明的默认优于开关）：来源在**这个项目里面**（子项目落地之后才有，§8）默认 `auto`——同一个人、同一棵树、一起走；来源在别处，以及今天所有的平的项目，默认 `manual`——别人的作品悄悄改了你的成品，正是 §2 里被否决的那种。面板里是一个小开关"自动保持最新"，改了就生效。

### 6.5 主题

链接的页是**成品**，带着来源自己的样子，不随目标的主题或设计系统变：文档穿了设计系统，画板的图片不会跟着变色（`docLook` 管文档自己的字和块，不管图片里的东西）；幻灯片的"切换主题"（`themeApply`）是改幻灯片文件里的颜色值，副本在 `uploads/` 里，不碰。这是对的：要同一套外观，就让来源和目标穿同一套设计系统。只有有明/暗两套的来源（看板的 `theme`、设计系统的主题）在元素上留一个"明 / 暗"的选择（默认明），图片和活的版本都按它画；其他来源不出现这一项。

### 6.6 导出

| 出口 | 图片形态 | 活的形态 |
|---|---|---|
| 文档的 Markdown / HTML / PDF / PNG / Word / 微信 | 就是一张图片，原样走（Markdown 的路径 `uploads/linked/…`，随 `images` 一起交出去） | 文档没有活的形态 |
| 幻灯片的单文件 HTML、放映 | 图片 | 画板：已有（`#dc-boards` 里一份运行时，每个嵌入建 iframe）；看板：同样多带一份看板运行时（体积在第 2 期量） |
| 幻灯片的 PDF | 图片 | Chrome 打印的是真页面，嵌入框架和画板今天怎么出就怎么出；看板要在第 2 期验证 |
| 幻灯片的 PPTX、PNG | 图片：PPTX 一张图、PNG 一张图 | 落成图片：先让"元素交出自己的图"（`frameSnap.ts` 的 `snapFrames`，动效已用，幻灯片还没接，import-from-project.md §5）；没接上之前这两条出口里是空的 |
| 动效的视频、GIF | 图片逐帧不变 | 画板：已有逐帧 seek；看板不进动效（§5） |
| 整个项目 zip | 记录和副本都进，原作品不进（子项目除外，§8） | 同左 |
| Claude Design 包 | 副本是 `uploads/` 里的普通文件，图片原样；记录是我们自己的键，Claude Design 格式不认，导出时忽略 | 同左 |

### 6.7 来源被删、被挪、不在这台机器上

- **副本一直在，元素一直照常显示**：这是选 C 的核心好处。
- 面板的来源行变成一句平静的话（不是红色错误，元素没坏）：原作品**已删除**（在回收站，[project-trash.md](./project-trash.md)）、**找不到**（句柄解析不到，比如换了台机器、zip 里没带）、或**在别处**（句柄变了但别名还在）。每种给下一步的物件：已删除→"恢复原作品"（打开回收站）；找不到→"重新指定…"（选一个项目，对上 `page`）；两者共有"断开链接（保留为图片）"。
- 断开 = 删掉记录，元素留下（图片形态就是一张普通图片；活的画板元素仍是画板的副本，仍能用）。一步撤销。

## 7. 界面

### 7.1 一个词

"导入"在产品里指把**文件**带进来；"引用"（References）指让 **Claude Code 去读**别的项目（[folder-groups.md](./folder-groups.md)）；"嵌入"（`<x-embed>`）是幻灯片里一段内联的小网页，也是给模型看的词。这三个词都被占了，所以这里**不新造一个和它们打架的词**：

- 人看到的动作：**"来自另一个项目的页面…"**（Insert 里的一项），选完得到的东西叫**链接的页面**（"Linked page"），因为它**带着来源**，能更新；
- "导入"这个词只留给文件；原来的"从项目导入…"改成这一项，不再多一个入口；
- 模型面向的文档（技能、提示）里写 *linked page*，说明它是 `uploads/linked/` 下的副本加 `imports` 记录，**不要手改**。

（用词是 §10 里要人定的一条。）

### 7.2 放进来：一处入口、一个选择器

每种类型都在"人放东西的地方"多一项，共用同一个选择器：

| 类型 | 入口 |
|---|---|
| 幻灯片 | 左侧插入栏（`SlidesBars`）和导入 / 导出菜单里 |
| 文档 | `/` 菜单（`DocEditor`）和导入 / 导出菜单里 |
| 画布 | 导入 / 导出菜单里（画板按钮的菜单是"新画板"，不放） |
| 动效 | 导入 / 导出菜单里 |
| 看板、设计系统 | 没有（§4.5） |

菜单里的措辞是真实的操作名（`importFilesLabel` 的做法）；`FileMenu` 的 `ImportControls.pickProject()` 已经为幻灯片和动效存在，推广成每个能接收的类型都有（`ImportTarget.board` 换成按类型的"这个类型能接什么"，数据来自 §5.1 的表，一张 `Record<ProjectKind, …>`，新类型缺了编译不过）。

**选择器**（今天的 `BoardPicker` 推广）：按"我要找什么"组织（ux-principles 第 1 条），不是按后端分类：

1. 顶上一行搜索（项目名、页名）；
2. 分组：**这个项目里面的**（子项目落地之后才有，§8）在最前，然后**同一个文件夹分组里的**，然后其他项目；
3. 每个项目下是它的页，**缩略图**（画板用画板运行时画、会动的悬停播放，今天已有；其他类型的页用最近一张缩略图或标题卡），一个类型小标签；
4. 页是否能放进当前作品，在选择器里**就是灰的、说明为什么**（"看板的页不能放进动效逐帧渲染的视频，可以放它的图片"），而不是点了才报错；
5. **不问"图片还是活的"**（消解模式选择，第 2 条）：按 §5.1 给默认——幻灯片、动效里画板和看板默认活的、其余图片；文档、画布只有图片。点一下页就放进来，放好后在面板里改（第 6 条）。

放在哪：放进幻灯片和动效就是当前页/场景，文档在光标所在块之后，画布在当前画板里选中位置或视口中心（沿用各类型"放一张图"今天的位置规则，不新定）。放好后元素处于选中状态，面板打开着。

### 7.3 面板：一张表单

选中链接的元素，右侧面板（沿用 `BoardEmbedProps` / "展开编辑" 的 Content 区，`ContentForm`，一个新类型的元素是 `editFields` 的一个新 case，不是新面板）：

| 行 | 内容 |
|---|---|
| 来源 | 项目名 › 页名，真实值（等宽的句柄在悬停里），旁边一个缩略图；子项目写"本项目里面" |
| 显示为 | 分段控件：**活的 / 图片**（只列该来源在该去处支持的，§5.1；只有一个就不出这一行） |
| 铺满方式 | 填满 / 完整显示（沿用 cover / contain） |
| （画板）旋钮 | Tweaks，和今天一样；还有"还原" |
| （会动的）时间 | 沿用画板的 `$time` 行；动效的 GIF 形态：封面帧 / GIF |
| （有明暗的）明 / 暗 | §6.5 |
| 状态行 | "已是最新" / "原作品在 2 天前改过 · **更新**"；"原作品已删除 · 恢复 / 断开"；"找不到原作品 · 重新指定 / 断开"；检查失败时写明原因 |
| 保持更新 | §6.4 的小开关"自动保持最新" |
| 动作 | **打开原作品**（在新标签页里，落在那一页）、**断开链接**（保留为图片，一步撤销） |

两条正交的轴（显示为、保持更新）不合并（第 4 条）；一行里只有一个关注点。**不增加**画布/页面上的任何装饰：元素本身看起来和普通图片、普通嵌入一样，只有选中时右下角出一个小的链接标记（`IconLink`，加进 `icons.tsx`）并在悬停里写来源，平时不加边框、不加角标（第 9 条，视觉噪声）。有过期时，选中才显示状态；项目级的提示只有项目菜单里的"更新所有链接的页面（N）"一处。

### 7.4 对 Claude Code

- 请求里（`Project settings now`，`settingsProject`）加一行"linked pages"：每个来源、页、形态和是否过期，让它知道哪些元素是副本、不要手改；每个类型的技能加一段 *linked pages*（`.claude/skills/<kind>/SKILL.md`、`delegate.ts` 的提示）；
- 改了链接（放进、断开、更新、换形态）走 `recordChange`，下一次请求告诉它；`followUp` 一般不出提议（一个更新不需要接着重排版），只有"换形态使尺寸变了很多"时才提议重排。
- 它想改来源的页：在来源项目里改，然后目标按 §6.2 更新；References（只读引用）已有的 `--add-dir` 与拒绝编辑规则不变，两件事互不依赖。

## 8. 和"嵌套子项目"的关系

另一个会话在先做"子项目"（`projects/<父>/<子>/`，分支 `tp/support-nested-sub-projects-994f9d`）。**分工已定：子项目只做子项目自己的动作，嵌入由这份方案负责，子项目不覆盖嵌入。** 所以这份方案**今天就能在平的项目上做完，不等子项目**：来源永远是"一个项目加一页"，用句柄找到，和它放在哪里无关。写这份时那个分支还没有任何改动（和 `main` 同一个提交，没有 issue、PR 或说明），下面是子项目落地后嵌入**怎样顺势用上它**，全部是可选的加成，不是前置条件。

| 事 | 今天（平的项目） | 子项目落地后 |
|---|---|---|
| 怎么指到来源 | 记录里 `from`（句柄，别名解析）+ `page` | 同样；子项目是一个有自己句柄的项目（句柄由路径生成，`project-identity.md`），嵌套路径照旧得到稳定句柄。再多记一个可选的 `rel`（相对本项目文件夹，如 `sub/hero`），解析时先看它，复制、fork、zip 之后仍然对得上；平的项目没有它，不受影响 |
| 选择器分组 | 同一个文件夹分组的项目，然后其他项目 | 多一组"这个项目里面的"，排在最前 |
| `sync` 默认 | 一律 `manual` | 来源在本项目里面的默认 `auto`（同一棵树，一起提交、一起打包）；由 `rel` 是否解析得到决定，不需要新字段 |
| zip 与提交 | 副本在包里，原作品不在，状态行写"原作品不在这里" | 父项目的包和提交若带上子项目（子项目那边的决定），原作品就在包里；嵌入不要求它做什么 |
| 被引用的页 | 页的编号规则不变（§4.2 的 `kind`、`page`） | 同样，子项目是个完整的项目 |
| 删除或挪出 | `from` 解析不到就是 §6.7 的"找不到"，副本照常 | `rel` 失效后退到 `from`，再失效同上 |
| 和 References（Claude 只读） | 不合并：References 是"Claude 改这个项目时可以读那些"，链接是"这个作品里有那一页" | 不变；子项目是否默认被 References 覆盖是子项目那边的决定 |

不需要子项目那边先答的问题：嵌入对它只有一个要求，**句柄能解析到子项目的文件夹**（`projectDir`、`resolveKey` 对嵌套路径可用），那是它自己动作的一部分。

## 9. 分期

每期单独可交付；都不改现有文件的含义，旧记录原样有效。

**第 1 期：一个模型、图片形态、能更新**

- 核心：`imports` 记录的推广（`BoardImport` → `LinkedPage`，读旧记录的缺省），`pageHash`，`LINKABLE: Record<ProjectKind, …>`（§5.1 的表）、检查（`uploads/linked/` 下的路径放行，`checkSlide`、文档图片、画布 `<img>`）；
- 服务端：`POST /api/projects/:p/link-page {from, page, mode}`（把现在的 `import-board` 推广：画板仍是复制，图片形态走 `pageExport` 出 PNG）、`POST …/link-refresh`、检查来源是否变了（读 `files`）；`projectArchive.ts` 的 `from` 改写；
- 编辑器：选择器（推广 `BoardPicker`）、六种类型里四种的入口、面板表单（`editFields` 的新 case）、状态行、"更新所有链接的页面"、断开、撤销；
- 把画板导入并进同一个入口和同一个面板，**加上"来源变了"**；
- 技能、`settingsProject`、`recordChange`、`e2e`：新套件 `linked_page`（文档 ← 画板的图、幻灯片 ← 看板的图、来源改了出提示、更新是一步撤销、来源删了元素仍在）。
- 先做三个小试验再动手（§10）。

**第 2 期**：幻灯片 ← 看板的活形态（冻结行）；幻灯片 PNG/PPTX/缩略图画出嵌入（接 `snapFrames`，这本来就是已有的缺口，也服务画板导入）；`auto` 同步；动效 → 幻灯片/文档的 GIF 形态；元素跨项目复制粘贴。

**子项目落地后（不阻塞任何一期）**：选择器多一组、`rel`、子项目来源的 `auto` 默认。

**第 3 期，按需**：幻灯片 ← 动效场景的活形态（要先定时间语义）、画布 ← 画板的活形态（`dc-import` 能否指到 `uploads/`）、文档的标签页只取一段、设计系统的页。

## 10. 还没定的（要人拍板的在最前）

**要人定：**

1. **采用 C（链接的副本）吗？**——保留"副本是运行时唯一真相、活引用继续否决"，把记录升级成可更新、可检查的链接。这是整份方案的前提；如果人要的是真正的活引用（原作品一改，这里立刻跟着变、副本不存在），那是 B，要推翻 import-from-project.md §2 的决定，范围和风险都大一个量级。
2. **用词**：这一项叫"来自另一个项目的页面…"、得到的东西叫"链接的页面"（§7.1）可以吗？备选："嵌入的页面"（但和 `<x-embed>`、文档里的嵌入撞）、"引用的页面"（和 References 撞）。
3. **第 1 期的范围**：只做"图片形态 + 来源变了提示 + 一键更新"，活的看板放第 2 期，可以吗？还是要幻灯片 ← 看板的活形态一起进第 1 期（工作量约翻一倍，且要先做看板喂数据的试验）。
4. **`auto` 同步的默认**：今天一律手动；子项目落地后，来源在本项目里面的默认自动（§6.4、§8）。这一条不阻塞第 1 期。

**要在实现开头用代码验证的：**

- 服务端能否用 `pageExport` 给**任意句柄的项目的任意一页**出 PNG（它为命令行和 `/mcp` 设计，`inServer` 参数在，没在这次设计里跑过）；
- 看板的数据集怎样交给沙箱框架（`DashApp` 约 157 行），嵌入能否复用同一段，冻结行（"暂停的查询"）的形状是否够；
- 画布的 `dc-import` 能否指到 `uploads/` 下的文件（决定画布 ← 画板能不能有活形态）；
- 动效 GIF 导出是否只在浏览器里（要不要 Chrome），决定"动效 → 别处"的第一版是否能在没有 Chrome 的机器上更新。

**开着的：**

- 页内的一部分（看板的一个图表、文档的一段、画板里的一个元素）：这一版以"页"为单位；"一个图表"要看板先给图表一个稳定编号（它今天只有整页）；
- 副本的清理：断开、删元素后 `uploads/linked/<id>/` 留不留（建议和别的 `uploads/` 一样留着，由"未使用的文件"清理统一处理，这一版不特判）；
- 同一页同时有"活的"和"图片"两种用法（§4.2）：副本里两份文件、记录里存一个 `mode`，还是记录改成按元素存？第 1 期先限制成一页一种形态，更新时一起换；
- 命令行和 MCP：`tingly-design link …`（放进、列出、更新、断开）。第 1 期不做，和 folder-groups.md §6 同一个理由，Claude 通过文件就能做，之后按需要加到 `commands.ts`。
