# parse5：仓库怎么用它，换成别的（包括 Go）行不行

状态：**研究**，不改产品代码。和 [server-runtime.md](../.design/server-runtime.md)（服务端换 Go）、[Go 移植验证：文档类型](../spikes/go-core/README.md)（把 core 移植成 Go）配套。验证代码在 [parse5-go-spike/](./parse5-go-spike/README.md)。

**一句话**：parse5 现在只在浏览器里跑，服务端从不解析画布和幻灯片；按 server-runtime.md 的"服务端不懂格式"方案，Go 服务端根本不需要它的替代品。如果以后真要在 Go 里解析，给 `x/net/html` 改约 55 行、再加一个 90 行的新文件，就能得到和 parse5 一样的源码位置：仓库里的全部模板逐项一致，html5lib 的 1791 个用例里有 1496 个连位置都一致，剩下的差异全在错误恢复的角落里。所以"Go 没有源码位置，画布和幻灯片最难迁"这个判断要改：难点不在解析器。

## 1. 仓库怎么用 parse5

只有一处：`packages/core/src/parse.ts` 的 `parseDc()`，版本 `parse5@8.0.1`（锁文件）。只调一个函数：

```ts
parseFragment(fragment, { sourceCodeLocationInfo: true })
```

- **输入**：画布 `.dc.html` 里 `<x-dc>` 和最后一个 `</x-dc>` 之间的文本；幻灯片是整个文件（一个 `<section>`）。`<x-dc>` 外面的东西（`<title>`、`data-dc-script`、`data-props`）用正则和手写扫描找，不经过 parse5。
- **上下文**：没传 context，parse5 默认用 `<template>` 作片段上下文，所以顶层可以直接写 `<tr>` 之类。
- **用到的树信息**：`tagName`、`namespaceURI`（区分 html / svg / math）、`attrs` 的 `name`/`value`/`prefix`（`xlink:href`）、`template` 的 `content`、文本和注释的内容。
- **用到的位置信息**（`sourceCodeLocation`），全部换算成整个文件里的下标：
  - 元素：整个元素 `startOffset`/`endOffset`、`startTag`、`endTag`（没写结束标签时没有），由此算出 `inner`（两个标签之间）；
  - 每个属性：`attrs[name]`，即 `name="value"` 整段的区间；
  - 文本、注释：各自的区间；
  - 解析器补出来的元素（`<table>` 里没写的 `<tbody>`）没有 `startTag`，`parseDc` 把它的子节点并到父节点里，画布上还会报"请显式写出"。
- **没用到**：行列号、`parse()` 整页解析、序列化、tree adapter、错误回调。

**位置信息被谁用**：`packages/core/src/copy.ts` 的 `DesignCopy` 是唯一的回写引擎。它从解析结果造一份 DOM，编辑完和原树比较，生成最小的文本替换：

| 改动 | 用到的区间 |
|---|---|
| 改一个属性 | 该属性的 `name="value"` 区间 |
| 删一个属性 | 属性区间，连同前面的空白 |
| 加属性 | 开始标签末尾（`>` 或 `/>` 前） |
| 改文字、注释 | 文本、注释节点的区间 |
| 子节点增删、换顺序 | 父元素的 `inner` 整段重写，但每个保留下来的子节点照抄它原来的源码（`range`） |
| 属性拿不到区间时 | 整个开始标签重写（兜底） |

另外 `elementSource()`（复制粘贴）、`slides.ts` 取元素原文、`setPropDefault()` 改 `data-props` 也靠这些区间。

**它在哪里跑**：全在浏览器。调用方是编辑器（`apps/editor/src/store.ts`、`fastedit.ts`、`motion.ts`、`slides/exportDeck.ts`）、沙箱运行时（`packages/sandbox/src/runtime.tsx`）和快速模型的 jQuery 执行器（`packages/core/src/exec.ts`，用页面的 DOM）。`apps/server` 一次都没调过 `parseDc` 或 `DesignCopy`，Claude Code 委托也是直接改文件。

## 2. parse5 的位置语义（任何替代品都要对齐的细节）

在 `parse5@8.0.1` 上实测：

- **下标是 UTF-16 码元**（JS 字符串下标），不是字节。`é😀` 占 3 个单位。Go 用字节，两边交换区间就要换算（文档类型的 Go 移植验证在评论锚点上也遇到过同一件事）。
- **省略结束标签**（`<p>a<p>b`、`<li>1<li>2`）：没有 `endTag`，`endOffset` 是让它结束的那个 token 的开头。
- **重复属性**：`<div a=1 A=2>` 只保留第一个，第二个在源码里但不在树里，也没有区间。
- **SVG 属性大小写**：`attrs` 里是 `viewBox`，位置表的键是小写 `viewbox`。`parseDc` 已经用小写兜底。
- **错位嵌套**（`<b>x<i>y</b>z</i>`）：重建格式元素时会克隆 `<i>`，parse5 让克隆出的第二个 `<i>` 带着和第一个相同的 `startTag`，区间还和前面的 `<b>` 重叠。（收养算法 `<a><p></a>` 产生的克隆则没有位置，按"补出来的元素"处理。）`parseDc` 只检查"补出来的元素"，没检查这种克隆，两个元素会拿到同一段源码。推断（未在编辑器里复现）：两个都被改时会撞上 `applyPatches` 的"overlapping patches"，父元素重排时会把 `<i>y` 抄两遍。模板是人和模型写的，错位嵌套不常见，但可以在 `parseDc` 里加一条"两个元素的开始标签相同就报错"。
- **parse5 自己的小毛病**：文件以没闭合的注释或 `<!`、`<?` 结尾时，注释的 `endOffset` 比文件长度多 1；以没闭合的 `<script>` 结尾时，元素区间是空的。只在残缺输入上出现。

## 3. 可选方案

| | 树和浏览器一致 | 元素、标签、属性区间 | 文本区间 | 说明 |
|---|---|---|---|---|
| **parse5（现状）** | 是，完整实现规范 | 都有 | 有 | JS 里唯一同时满足两列的库。打包后 151 KB，gzip 42 KB（只引 `parseFragment`） |
| htmlparser2 | 否：不补 `<tbody>`、不做收养算法、不区分外来命名空间 | 只有元素的 `startIndex`/`endIndex`，没有标签、属性区间 | 有 | 快，但回写要的东西缺一半 |
| 浏览器 `DOMParser` | 是 | 没有 | 没有 | 不可用 |
| Go `x/net/html` 原样 | 是（个别新规范没跟上，见 §4） | 没有 | 没有 | 分词器的 `Raw()` 可以累加出 token 的字节位置，维护者在 [golang/go#34302](https://github.com/golang/go/issues/34302) 里确认过这种用法，但树节点不带位置，属性区间也不导出。提案仍开着，不会很快进标准库 |
| **Go：给 `x/net/html` 加位置（验证过）** | 同上 | 都有 | 有 | 见 §4 |
| Go：tdewolff/parse 的 html 词法器 | 否，只有词法，不建树 | 能拿到 token 位置 | 有 | 树要自己建，等于重写规范的建树部分 |
| Go：手写简化解析器 | 只覆盖模板允许的写法 | 自己定 | 自己定 | 模板是受约束的子集，看起来够用；但沙箱里渲染的是浏览器建的树，凡是浏览器和它不一致的写法都会让"改的是 A、存下来是 B"，只能靠对照用例兜 |
| Go 里跑 parse5（goja、QuickJS/wazero） | 是 | 都有 | 有 | 和 server-runtime.md 方案 D 的问题一样：多一种运行时，调试和性能都差 |
| Rust html5ever、C Gumbo | 是 | 没有字节区间（html5ever 只有行号） | — | 不考虑 |

## 4. Go 验证：给 x/net/html 加源码位置

做法：复制 `golang.org/x/net v0.61.0` 的 `html` 包，改动集中在一个新文件里，`parse.go`、`node.go` 只加挂钩（约 55 行）：

- 解析循环每读一个 token，用 `len(Raw())` 累加出它的字节区间；
- 分词器导出每个属性的区间（它本来就记着，只是没公开），对齐到 `Token().Attr`；
- 建元素、建文本、建注释时记下当前 token 的区间；`parseImpliedToken` 补出来的元素、`</br>` 变成的 `<br>`、收养算法的克隆都不记，重建格式元素的克隆复制原元素的位置，这几条都照 parse5 的做法；
- 不去改 60 多处出栈的地方，而是每处理完一个 token，看哪些元素离开了打开元素栈：如果当前 token 就是它的结束标签，记为 `endTag`；否则以当前 token 的开头作为结束。这正是 parse5 的规则。

对照方法：同一段输入，两边都以 `<template>` 为上下文解析片段，输出带区间的树（parse5 的 UTF-16 下标换算成字节），逐行比较。

| 用例 | 数量 | 树和全部区间都一致 | 只有区间不同 | 树不同 |
|---|---|---|---|---|
| 仓库里的画布和幻灯片模板（`projects/`、`e2e/` 等，不含 `artifact/`） | 25 | **25** | 0 | 0 |
| html5lib 建树测试的全部输入（专门测错误恢复） | 1791 | **1496** | 268 | 27 |

区间不同的 268 个全是错误恢复，一个用例可能占几类：179 个是元素到文件末尾都没闭合（parse5 的结尾位置规则不统一，见 §2）；47 个是被规范丢掉的字符（NUL、`<pre>` 后的第一个换行，parse5 不算进文本，Go 算进）；43 个是错位嵌套、表格里的 `<form>` 这类没有结束标签的元素，结尾位置算法不同；14 个是 §2 说的 parse5 注释越界；只有 2 个开始或结束标签的区间不同（svg 里的 `<td>`、`<template>` 碰上同名的 HTML 结束标签，parse5 把结束标签记给了 svg 元素）。属性区间没有一个不同。

树不同的 27 个几乎都是 `<select>` 里放 `<button>`、`<div>`、`<svg>`、`<datalist>`（规范近两年为可定制下拉框改了 select 的解析，两个库跟进程度不同），另有一两个 `<font>` 嵌套和半截标签。这些写法不会出现在画布模板里。

耗时（同一台机器，含位置信息）：仓库模板平均每个 parse5 0.2 ms、Go 0.13 ms；把全部模板拼成 790 KB 的一份，parse5 65 ms、Go 23 ms。

代价：要维护一份 `x/net/html` 的分支。这个包改动很少，挂钩点集中，跟上游合并的成本低；也可以等 #34302 的 `RawTagAttr` 之类进上游后缩小改动，但不能指望。

## 5. 结论

1. **服务端换 Go 不受 parse5 影响。** 按 server-runtime.md 的边界原则，解析和回写留在浏览器，parse5 原样保留。现在的代码已经是这样。
2. **如果以后要在 Go 里理解画布和幻灯片**（服务端校验、服务端执行编辑、把 core 整体编成 WASM），用"x/net/html 加位置"这条路，并照文档类型 Go 移植验证的做法用对照用例兜底：仓库模板加 html5lib 输入，两边逐行比较。解析器本身已经验证可行，真正的工作量在 `copy.ts` 的回写：它依赖一个可变的 DOM（jQuery 和人的编辑都在 DOM 上做），Go 里要有对应的 DOM 操作和序列化，还要处理 UTF-16 和字节两种下标。这才是下一个该验证的东西。
3. **不建议**：换 htmlparser2（位置不够、树和浏览器不一致）；手写简化解析器（和沙箱里浏览器的树会悄悄不一致）；在 Go 里嵌 JS 跑 parse5。

## 6. 和解析器无关、但对照时发现的两件事

- **错位嵌套产生共享源码的克隆元素**（§2），`parseDc` 没拦。可以加一条检查，和"补出来的元素"一样报给作者。
- **parse5 在残缺结尾上的位置不统一**（注释越界 1、未闭合 `<script>` 区间为空）。模板正常保存时不会以残缺结尾，影响很小；Go 版如果要逐字节对照，这几类用例需要标成已知差异。

## 7. 开放问题

- core 要不要移植成 Go（文档类型的 Go 移植验证在问的问题）？如果答案是"不移植，服务端只做薄宿主"，这份调研只剩第 6 节有实际用处。
- 如果移植：Go 侧的可变 DOM 用什么（自己在 `html.Node` 上实现 `DesignCopy` 需要的那一小组操作，还是找现成的），以及浏览器和 Go 之间传区间时统一用哪种下标。
